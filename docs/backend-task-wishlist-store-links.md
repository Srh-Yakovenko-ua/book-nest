# Backend task — звести «де купити» до `BookStoreLink`

## Контекст

Магазин і ціна книги, яку користувач хоче купити, зараз пишуться **у дві різні таблиці
залежно від того, яким шляхом їх ввели**, а сторінка «Список бажань» читає лише одну з них.
Через це введені дані невидимі.

Знайдено на живих даних (dev, книга `84fd03a8-3c98-42fc-9260-e8049556befe` «Диявол носить чорне»):

| Джерело                                          | Відповідь                                                                                 |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `GET /api/books/wishlist` → `books[].storeLinks` | `[]`                                                                                      |
| `GET /api/books/:id/store-links`                 | `{ storeLinks: [], bestOffer: null }`                                                     |
| `GET /api/books/:id` → `purchaseInfo`            | `{ storeName: "КСД", storeUrl: "https://ksd.ua/…", expectedPrice: 380, currency: "UAH" }` |

## Дві моделі для одного поняття

| Модель                                                               | Поля                                                                        | Хто пише                                                                                                                                                                   |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BookPurchaseInfo` (1:1, `book_purchase_info`)                       | `storeName`, `storeUrl`, `expectedPrice`, `currency`, `note`, `purchasedAt` | `computeOwnershipChange({ kind: "want-to-buy" })` → `buildWantToBuyOverwrite` (`apps/api/src/modules/books/domain/ownership-transition.ts:63`) і `{ kind: "mark-bought" }` |
| `BookStoreLink` (1:N, `book_store_links`, `@@unique([bookId, url])`) | `storeName`, `url`, `price`, `currency`                                     | `POST /api/books/:id/store-links`                                                                                                                                          |

Уся цінова частина сторінки бажань — рядок книги, `bestOffer`, чіпи `Є посилання` / `З ціною`,
лічильник «Магазинів відстежується», блок «Найвигідніші пропозиції» — читає **тільки**
`storeLinks` (`wishlistWithRelations`, `apps/api/src/modules/books/infrastructure/books.repository.ts:112`).

## Масштаб на живих даних

Заміряно на dev-акаунті через `GET /api/books/wishlist`:

| Показник                                   | Книг   |
| ------------------------------------------ | ------ |
| у списку бажань                            | 33     |
| мають `storeLinks`                         | **0**  |
| мають `purchaseInfo` з магазином або ціною | **31** |
| мають `purchaseInfo.storeUrl`              | 29     |
| мають і `storeUrl`, і `expectedPrice`      | 28     |
| мають `storeUrl` без `storeName`           | 1      |
| мають `expectedPrice` **без** `storeUrl`   | **2**  |
| мають `note`                               | 0      |
| дублікатів `storeUrl` у межах книги        | 0      |

Тобто вся статистика сторінки показує нулі не тому, що користувач нею не користувався, а тому
що його дані лежать у гілці, якої сторінка не бачить.

## Рішення

`BookStoreLink` стає **єдиним** джерелом «де можна купити і за скільки».
`BookPurchaseInfo` лишається описом **факту покупки**.

Важливо: поля `storeName` / `expectedPrice` / `currency` з `BookPurchaseInfo` **не видаляються** —
для купленої книги («купила в КСД за 380») вони законні. Змінюється лише **шлях запису до
покупки**: перехід `want-to-buy` більше не пише в них.

## Межі

- **Схема не змінюється.** Нових колонок і полів немає — тільки міграція даних.
- Зміна ламає контракт `WantToBuyInput`; фронт оновлюється в тому ж слайсі.
- Шари: домен лишається чистим, створення посилання оркеструє сервіс у транзакції.
- Міграція даних — окремим кроком, **неруйнівна**, з логом того, що не перенеслося.

---

# 1. Шлях запису

## 1.1 Домен

`apps/api/src/modules/books/domain/ownership-transition.ts` — прибрати `buildWantToBuyOverwrite`.
Перехід `want-to-buy` більше не чіпає `purchaseInfo`:

```ts
case "want-to-buy":
  return { book: { ownershipStatus: "want_to_buy" } };
```

`OwnershipTransitionInput` для цього kind більше не потребує `fields`.

## 1.2 Контракт

`packages/shared/src/books.ts`:

```ts
export const WantToBuyInputSchema = z.object({
  storeLink: CreateBookStoreLinkInputSchema.optional(),
});
```

`CreateBookStoreLinkInput` вимагає **і** `url`, **і** непорожній `storeName`
(`packages/shared/src/book-store-links.ts:27`), тому часткові дані відсікаються на межі, а не
всередині.

> **Чому не лишити плоскі поля.** Плоскі `storeName` / `storeUrl` / `expectedPrice` дозволяють
> ввести ціну без магазину — стан, який `BookStoreLink` виразити не може. Саме через нього
> в даних утворилися 2 книги, які нікуди не мігрують. Вкладений об'єкт робить невалідний стан
> невиразним.

## 1.3 Сервіс

`apps/api/src/modules/books/application/book-ownership.service.ts` → `wantToBuy`:

у `TransactionRunner.run`:

1. застосувати зміну володіння (як зараз, `applyGuardedOwnershipChange`);
2. якщо `input.storeLink` заданий — створити `BookStoreLink` тим самим репозиторієм, що й
   `POST /:id/store-links`, з тими самими перевірками: ліміт `MAX_STORE_LINKS_PER_BOOK = 20`
   і `@@unique([bookId, url])`;
3. на P2002 по `book_store_links_bookId_url_key` — **не падати**: посилання на цей магазин уже є,
   це не помилка користувача. Оновити ціну наявного запису.

Обидві дії в одній транзакції: статус без посилання лишає користувача з тим самим порожнім
рядком, який ми й лагодимо.

# 2. Міграція даних

Два кроки, **між ними перевірка**. Не об'єднувати.

## 2.1 Крок A — перенести (неруйнівний)

Для кожного `book_purchase_info`, де `purchased_at IS NULL` **і** `store_url IS NOT NULL`,
створити `book_store_links`:

| Колонка посилання | Джерело                                                                                   |
| ----------------- | ----------------------------------------------------------------------------------------- |
| `url`             | `purchase_info.store_url`                                                                 |
| `store_name`      | `purchase_info.store_name`, а якщо порожній — **хост із URL** (`ksd.ua`)                  |
| `price`           | `purchase_info.expected_price`                                                            |
| `currency`        | `purchase_info.currency`, а якщо порожня при непорожній ціні — `UAH` (`DEFAULT_CURRENCY`) |
| `user_id`         | `books.user_id`                                                                           |

- `ON CONFLICT (book_id, url) DO NOTHING` — повторний запуск безпечний.
- `purchase_info` **не чіпати** на цьому кроці.
- Умова `purchased_at IS NULL` навмисна: у купленої книги `store_name`/`expected_price` описують
  здійснену покупку і переїзду не підлягають.

**Що не перенесеться:** рядки з ціною без `store_url` (на dev — 2 книги). Їх треба
**порахувати й вивести в лог міграції**, а не проковтнути.

## 2.2 Крок B — прибрати дубль (після перевірки)

Окремою міграцією, коли крок A підтверджено на проді: для рядків із `purchased_at IS NULL`,
у яких **уже існує** відповідне `book_store_links` з тим самим `url`, занулити
`store_name`, `store_url`, `expected_price`, `currency`.

Рядки без парного посилання (ті самі 2 книги) лишити недоторканими.

## 2.3 Рев'ю

Делегувати `migration-reviewer`. Очікувано: `INSERT ... SELECT` і `UPDATE` без DDL, без блокувань
на великих таблицях. Крок B класифікується як **DESTRUCTIVE** (стирає значення) — саме тому він
окремий і йде після перевірки.

---

# 3. Фронт

- Діалог `want-to-buy-dialog.tsx` шле `storeLink: { url, storeName, price, currency }` замість
  плоских полів; `storeName` і `url` стають обов'язковими разом, ціна — ні.
- Якщо користувач хоче лише зафіксувати очікувану ціну без магазину — цього шляху більше немає;
  або магазин із посиланням, або нічого. Це свідоме звуження: саме воно й породило невидимі дані.
- Блок покупки на сторінці книги показує `purchaseInfo` тільки для купленої книги; для
  `want_to_buy` джерело — `storeLinks`.
- Після успіху інвалідувати `storeLinkKeys.forBook(bookId)` і ключ списку бажань.

---

# 4. Тести

**Домен:** `want-to-buy` більше не повертає `purchaseInfo` у патчі.

**Сервіс:**

- `wantToBuy` без `storeLink` — статус змінюється, посилань не створено;
- зі `storeLink` — створено рівно одне, ціна й валюта на місці;
- повторний виклик із тим самим `url` — не 409, а оновлення ціни наявного;
- 21-ше посилання — помилка ліміту;
- падіння на створенні посилання відкочує і зміну статусу (одна транзакція).

**Міграція (інтеграційно, на реальній БД):**

- рядок із `store_url` → створено посилання з правильними полями;
- `store_name` порожній → взято хост із URL;
- ціна без `store_url` → посилання не створено, лічильник пропущених зріс;
- `purchased_at IS NOT NULL` → не чіпається;
- повторний прогін кроку A нічого не дублює.
