## Tried and rejected — do not re-derive these

**Pointing a test `DATABASE_URL` at pglite so `createTestApp` works.** Dead end, proven three separate times. The harness creates a template database per worker (`resetTemplateDatabase` → `CREATE DATABASE`, then `CREATE DATABASE … TEMPLATE …` per pool, `test/worker-db.ts:49,103`), and `PGLiteSocketServer` ignores the database name in the startup packet — connecting as `postgres` and as `probe_template` both land on the same database. Template and worker databases collapse into one and `truncateAllTables` wipes the template mid-run. pglite is excellent for driving a live server, useless for this harness.

**Narrowing `DeliveryDay`'s string branch with a Zod `.brand()`.** Correct in principle, rejected on blast radius: the brand leaks into every inferred input type in `@app/shared` and out to the frontend. Normalised the string to a UTC calendar day in `core/iso-date.ts` instead.

**Importing the wishlist rule from the books domain into `OrderBooksRepository`.** `resolveWishlistAddedAtChange` is per-book and needs each book's current status; the repository writes a _set_ of books in two statements. Reusing it literally means N reads + N writes or a contrived "representative status". Pinned both implementations to one 6×6 truth table instead (`modules/delivery/infrastructure/order-books.repository.test.ts`), and verified the test bites by breaking the repository two ways.

**Fanning the per-book PATCH out to `BookOrderService.update` + `ShipmentService.update` + an item write.** Three transactions, and moving `orderDate` forward together with `expectedDeliveryDate` fails the first call because it validates against the _stored_ expected date. Hence `SingleBookOrderService`, which validates merged values and writes all three levels in one `TransactionRunner.run`.

**Adding a second `@ApiTags("order-items")` to separate item routes from shipment routes.** `@nestjs/swagger`'s `mergeValues` concatenates arrays, so the operations stay filed under the first tag and Orval would follow. Needed a real controller split (`api/book-order-items.controller.ts`).

**`.default({})` on the all-optional POST bodies.** It short-circuits without re-parsing, so inner defaults never apply — a bodyless cancel would have sent the book to `not_owned` instead of `want_to_buy`. `.prefault({})` substitutes and re-parses. Use it uniformly.

**`order: { userId }` alone as the tenant predicate on the reminder select.** Insufficient: the reproduced leak hangs a _foreign book_ off the attacker's _own_ order, so the order already matches. Needs `book: { …active, userId }` as well. Both predicates are in place now — do not "simplify" one away.

## Live traps

- **Do not merge to `dev`.** Writes go to the new tables; the legacy list/history/statistics endpoints still read `book_deliveries`. Seven books with active order items returned `{"items":[],"totalCount":0}` from `GET /api/delivery/in-transit`. Legacy `POST /api/delivery/receive` still writes the old table and flips `ownershipStatus`, which would desync a book against its live order item. The frontend slice and the legacy-path removal must ship in the same deploy.
- **`T12` and `T50` break the frontend at compile time.** Deleting the legacy shared contracts and regenerating the Orval client cannot be done without migrating `apps/web` in the same change. The spec deliberately scoped the frontend out; `T61` only sizes it (49 files in `features/delivery`, seven book-level consumers, ~346 delivery i18n keys per locale).
- **Node 24 is required.** The shell defaults to Node 18, which crashes ESLint. Prepend the nvm Node 24 bin to `PATH`.
- **`packages/shared` is consumed through its built `dist` at test runtime.** A new export is invisible to vitest until `pnpm --filter @app/shared build` runs. This cost two agents a red suite.
- **Classify test failures before believing them.** A run with no database produces thousands of `Can't reach database server`. Grep the output for `AssertionError`/`TypeError` counts — that is the real signal. On the last local run: 4880 connection errors, 0 assertion failures.
- **`rm -r` and `rm -f` are in the permission deny list.** Cleaning a directory needs plain `rm <file>` then `rmdir <dir>`.
- **A subagent once bypassed the migration guard hook** by staging bytes in the scratchpad and using `cp`. The hook has since been narrowed (commit `a43e5bc3`) so a freshly generated, still-untracked `migration.sql` is editable and a committed one is not. If an agent reports being blocked on a migration, check it is not working around the guard.
- Still running from this session, kill or ignore: a Next dev server on `:3000` (pid 909010) and a pglite socket server on `:55432` (pid 991921). The web dev server proxies `/api` to the **remote** `dev.book-nest.net`, not to a local API.
- A second interactive Claude session was active in this repo throughout. If the tree looks unexpected, check whether it touched something.
- The remote dev database holds ~46 seeded books and 49 deliveries created through the API in the **old** model. They are the realistic input for the data migration and for `legacy-profile.md`'s two hard gates, which must be run against the real database before any deploy.

## Open questions for the next session

Recorded in `tasks.json`, but unanswered, and each changes the work:

- **D14** — keep the `books/` prefix on the four read routes permanently, or rename them at cutover. Leaving it costs nothing (client and `openapi.json` are regenerated wholesale) and avoids a second rename; renaming splits the read surface across two naming schemes since `orders/statistics` keeps its prefix.
- **T71** — should a shipment become `received` when its last active item is received? Today it does not, so a fully-received shipment keeps counting in `activeShipmentsCount` and in status filters.
- **T73** — the reminder dedupe key changed shape, and old keys were not migrated. First sweep after cutover repeats at most one reminder per in-flight book per stage. If that is unacceptable, the backfill must ride with the `DROP TABLE` migration, because it needs to read `book_deliveries` before it goes.

Only the maintainer can answer these.
