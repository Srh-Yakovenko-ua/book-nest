## Етап A. Доменна коректність — перед UI

### RG-01 — правильний лічильник подій `book_counted`

**Проблема:** `reading-goal-sync.service.ts`, `countedRows`: для нового зарахування записує `completedCount: index + 1` із поточного набору, відсортованого за `finishedAt`/UUID; за однакової або введеної заднім числом дати нова подія може отримати `1`, коли раніше уже зараховано 1 книгу.

**Очікувана семантика:** `metadata.completedCount` — скільки книг зараховано **після цієї події**, у порядку фактичного запису переходів, а не порядку за датою прочитання. Для однієї нової книги при поточних 1/5 записати 2/5. Для множинних нових зарахувань у межах однієї операції створити детермінований порядок і послідовні значення. Для зняття зарахування й повторного зарахування коректно врахувати актуальний стан на момент події.

**Реалізація:**

- У `apps/api/src/modules/reading-goals/application/reading-goal-sync.service.ts` відокремити фактичний стан до змін і після змін, визначити базовий count для `book_counted` без орієнтації на `qualifying.index`.
- Переглянути `reading-goal-activity.recorder.ts` (створення цілі, зміна дедлайну) — така сама семантика у всіх джерелах `book_counted`. Не дублювати обчислення, якщо можливо винести чисту функцію.
- Зберегти `finishedAt` як фактичну дату прочитання, `createdAt` події — як час запису; не плутати дві шкали часу.
- Після зміни кодової логіки старі некоректні `metadata` **не виправляться самі**. Додати окрему, безпечну, ідемпотентну процедуру/dry-run-план реконструкції старих подій (ordered by createdAt + deterministic tie break, з урахуванням `book_uncounted`, старих станів, ambiguous ties). Виконання на даних користувачів — **не автоматичне**; якщо реконструкція неоднозначна, логувати й пропускати з описом.

**Критерії:** `1/5 → 2/5` при однаковій даті; заднім числом; `book_uncounted` → повторне зарахування; створення з кількома qualifying; історія не змінює вже зафіксовані події без явного backfill.

### RG-02 — узгодити ризик із прогнозованим запізненням

**Проблема:** `on_track` із допуском ±0,5 книги може співіснувати з прогнозованим запізненням на 15 днів. У `reading-goal-risk.ts` `projectedDaysDelta < 0` фактично не створює причини ризику, а `attention` включає лише `behind`/`critical` або high/critical risk.

**Рішення на рівні контракту:** додати `projected_late` до `ReadingGoalRiskReasonSchema` у `packages/shared/src/reading-goals.ts` із повним оновленням exhaustiveness-switches, локалізацій, generated types (за офіційним процесом codegen) та тестів. Не змінювати enum темпу чи формулу його допуску.

**Рекомендована технічна модель порогів v1 (нова деталізація, не окремо погоджена раніше):** для **активної** цілі і **достатньо надійного прогнозу** (`projectionConfidence` = `medium` або `high`) з `projectedDaysDelta < 0` визначити `lateDays = abs(projectedDaysDelta)`:

| Прогнозоване запізнення | Мінімальна оцінка ризику |
| ----------------------- | ------------------------ |
| 1–3 дні                 | `low`                    |
| 4–7 днів                | `medium`                 |
| 8+ днів                 | `high`                   |

`critical` залишити за існуючими критичними правилами темпу/комбінацій; не робити прогноз 15 днів автоматично `critical`, якщо до дедлайну ще є 38 днів. Результуючий `riskLevel` — **максимум** ризику від чинних правил і прогнозу, ніколи не занижувати наявний високий/критичний рівень. Для `none` або `low` confidence не робити висновків на основі дати прогнозу; зберегти інші правила ризику. `projected_late` не означає, що поточний темп перейменовується на `behind`.

`needsReadingGoalAttention`: цілі з high/critical risk уже входять у блок; переконатися, що `projected_late` з 8+ днями та medium/high confidence потрапляє туди, а текст причини пояснює прогноз (наприклад, «За поточним темпом завершення може запізнитися на 15 днів»). Для 1–7 днів не форсувати окреме KPI attention без додаткових причин, щоб не створити надмірні тривоги. Показувати причину в деталях навіть для low/medium. Не змінювати математичний `projectedCompletionDate`.

**Точки змін:** `reading-goal-risk.ts`, `reading-goal-attention.ts`, `reading-goal-metrics.ts` (передати confidence у ризик), `reading-goal.constants.ts`, shared schema/types, FE `goal-overview-tab.tsx`, `goals-overview-highlights.tsx`, `messages/uk.json`, `messages/en.json`, tests. Перевірити вплив на KPI і `risk_desc`.

**Очікувано для тестового стану:** `pace=on_track` залишається; `riskLevel=high`, `riskReasons` включає `projected_late`, у блоці уваги з'являється одна ціль. У UI пояснюється: «Близько до плану за поточним прогресом, проте прогноз показує ризик запізнення».

### RG-03 — назва цілі без власної назви

Єдина FE-функція для відображення title: якщо `goal.name` задана — показати її без зміни; інакше компактне «Прочитати N книг» (правильне українське відмінювання через next-intl), а дедлайн — **окремо**. У каталозі, блокові уваги, hero, бічній картці та історії уникати трьох різних fallback-назв одного об'єкта. Плейсхолдер форми може залишатися пояснювальним прикладом і **не є самою назвою**. Показати джерельний список окремим рядком/посиланням. EN локалізація — аналогічно.

### RG-04 — досягнуто пізніше, а не просто «Пропущено»

Не змінювати `ReadingGoalCheckpointStatusSchema` і бекенд-дані: `status=missed` описує своєчасність, `achievedAt!=null` — факт досягнення. На UI виводити похідний стан:

- `achievedAt` існує і `achievedAt <= dueDate`: «Досягнуто» (успіх);
- `achievedAt` існує і `achievedAt > dueDate`: «Досягнуто із запізненням» (попередження + фактична дата);
- `achievedAt=null`, `status=missed`: «Пропущено»;
- інакше: «Попереду».

Зауважити, що checkpoint з `status=missed`/`achievedAt` у старій логіці вже має текст «досягнуто пізніше», але бейдж неправильний. Прогрес за день дедлайну включно. Показувати різницю дат, якщо вона може бути достовірно розрахована; не обов'язково додавати нове поле API.

### RG-05 — `GoalFormDialog`/валідність кнопки

- Форма не повинна дозволяти submit за невалідних `targetCount` (0, понад кількість snapshot-книг, >1000), `deadline` чи інших полів, а не лише відхиляти submit через resolver.
- Встановити коректну реактивну валідність (`formState.isValid` з відповідним режимом валідації) + `isPending` + unchanged у режимі edit.
- Повідомлення «У цілі 5 книг» та «У цілі лише 5 книг» не повинні дублюватися при помилці. Не послаблювати server-side Zod валідацію.
- Зберегти cancel, dirty-close-confirmation, focus return, presests, date picker, i18n.

## Етап B. Спільний header і hero трьох вкладок

**Ціль:** замінити подвоєні «прогрес/час» і надто високий header, не приховавши суттєвих фактів.

**Desktop header:** назад до джерельного списку (якщо є), title (`name` або compact fallback), статус, метадані (джерельний список, дедлайн), дії Edit / Archive / Delete для дозволених статусів. Зберегти семантику archive/delete та confirm-dialog. Кнопки не дублювати у вкладках.

**Hero (спільний для всіх tabs):** великий `%`, `completedCount із targetCount`, progress bar 0–100, маркер плану (`elapsedPercent` як частка тривалості, лінійна ціль), легенда «Фактично»/«План на сьогодні», `daysLeft` для активної або достовірна мітка завершення/прострочення/архіву. Показати відхилення від очікуваного числа книг `paceDeltaBooks` з поясненням. Умовно рендерити метрики: не показувати `daysLeft` при null, не показувати хибні 100% до завершення.

**Status cases:** active, completed, expired, archived; архівована ціль не редагується, але залишається доступною в каталозі; завершена має святковий, **не надмірний** акцент. «До дедлайну» лише для active; якщо потрібен бейдж наближення до плану, він є **лейблом пояснення**, не новим enum.

**Responsive:** на 390px back/title, active badge, Edit + ellipsis; Архів/Видалити у меню з коректними aria labels, клавіатурною навігацією й підтвердженнями; hero одним екраном не витісняє tabs; на ширших екранах інлайн-дії. Без sticky tabs у цьому етапі. Немає overflow-x.

**Не створювати** сторонній duplicate progress component без повторного використання наявних `GoalDetailHeader`/`GoalDetailsView`, `Progress`, Badge, PageTabs.

## Етап C. Вкладка «Огляд»

### C1. «Темп і прогноз»

Замість чотирьох рівнозначних карток «Прогрес і час» / «Темп» / «Ризики» / «Прогноз»:

- «Темп і прогноз» з current rate, required rate, дельтою в книгах та прогнозованою датою, впевненістю. `averageDaysPerBook`, `requiredDaysPerBook` — основний спосіб подання; числа `actualBooksPerDay`/`requiredBooksPerDay` можна залишити в допінфо. Для `null`/`0` використовувати осмислені відсутні стани.
- Не називати `medium` forecast «точним», пояснити, що розрахунок орієнтовний і ґрунтується на кількості зарахованих книг.
- Якщо confidence `none`/`low`, замість великої порожньої картки — компактне пояснення «Для прогнозу потрібно більше зарахованих книг», із доречною невеликою ілюстрацією/іконкою.
- Різницю між `pace=on_track` та невеликим від'ємним `paceDeltaBooks` пояснювати в тексті/tooltip; не змінювати статус розрахунку.

### C2. «Стан цілі»

- Чітко показати riskLevel і всі релевантні `riskReasons`; окремо пояснювати `projected_late`.
- Якщо ризик є — дати практичний наступний крок **лише на підставі даних**: «Для виконання цілі потрібно приблизно 1 книга кожні N днів», де N із `requiredDaysPerBook`, або перехід до книг. Не обіцяти, що конкретний крок гарантовано ліквідує ризик.
- Коли riskLevel none — компактна нейтральна констатація, не створювати порожню картку заввишки 200px.
- Повідомлення про deadline soon / no recent progress не дублювати у кількох картках.

### C3. Контрольні точки

- Рендерити **усі** `checkpoints` (зараз максимум 5), дата `dueDate`, цільова кількість, фактичний `achievedAt`, похідний лейбл стану з RG-04.
- Desktop timeline лінія + маркери; mobile вертикальна лінія. Не вводити горизонтальний скрол для 5 елементів на мобільному.
- Підпис «2 із 5 досягнуто із запізненням» використовувати, тільки якщо це випливає з даних. Статус не визначати з `currentCompletedCount` сам по собі: враховувати `achievedAt`.

## Етап D. Вкладка «Книги»

- Використовувати існуючий endpoint `/goals/:id/books`, scope `all/counted/remaining`, cursor pagination, TanStack Query та існуючі інвалідації.
- Desktop при достатній ширині — дві колонки компактних книжкових карток; laptop/tablet/mobile — одна, без переповнення та неприродних висот. Однакова логіка всіх трьох scope.
- Фільтри з counts: `Усі · snapshotBookCount`, `Зараховані · completedCount`, `Ще не зараховані · max(snapshotBookCount - completedCount,0)`. При видалених/недоступних книгах не вигадувати числа; якщо API не гарантує точність цього співвідношення, використовувати фактичне узгоджене джерело або нейтральні лейбли.
- Назва, обкладинка, автор, стан, дата зарахування/не-зарахування; для `reading/paused/rereading` зі сторінками — мінібар та `currentPage/pagesCount`, % clamped 0..100. Не рахувати книгу зарахованою до `qualifies=true`.
- Пояснення frozen snapshot компактним рядком із можливістю детальнішої довідки, не прибирати принципову інформацію.
- Сортування з однаковим `finishedAt`: розглянути стабільний tie-break за `snapshotPosition`, далі UUID, але синхронно оновити cursor comparator + відповідні тести. Не вводити нову UI-сортувалку лише заради макета.
- Зберегти посилання на сторінку книги; не додавати кнопку зміни reading-status прямо у книжкову картку цілі.

Мінімізувати зміни схем БД: `projected_late` — **нове значення існуючого API enum**, не нова таблиця; checkpoint — лише FE interpretation. Конкретні назви компонентів Claude має обрати після перевірки поточної структури, без надмірного абстрагування.

## Out of scope

Створення річних/сторінкових/часових цілей, глобальний пошук у цілях, нова адміністративна панель seed-даних, цілковитий редизайн статистики/списків, зміна формули `pace`, зміна `successRate`, повна перебудова БД, нові scheduled jobs, нові залежності UI без необхідності.

### F-Assets — інтеграція 5 затверджених PNG (доповнення v3)

Використай карту з `04_ILLUSTRATIONS_USAGE.md` як обов’язкову частину етапу F. Мапінг семантичних станів має залишатися точним: `expired` використовує годинник; `completed` — кубок; прогноз із запізненням активної цілі **не** означає `expired`. Порожній каталог показує «Перша ціль», а counted-filter empty показує «Ще не зараховано». Не додавай ілюстрації до звичайних непорожніх карток книг і KPI, щоб не перевантажити UI.
