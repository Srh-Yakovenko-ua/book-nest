# Reading Goals — Acceptance Criteria та регресії v1

## Стратегія перевірок

Під час реалізації **не запускати build, ESLint, typecheck або весь suite після кожного етапу**. Claude Code має робити розумну локальну перевірку коду, а наприкінці — **один фінальний погоджений прогін**: відповідні unit/component tests за зміненими доменами, TypeScript check для зачеплених workspace, ESLint для змінених файлів і за необхідності один build web/api. Якщо фінішний прогін виявляє помилки — виправляти конкретні причини та повторити тільки відповідну перевірку. Не відключати тести/правила та не маскувати TypeScript помилки.

## Візуальні вимоги (важливіше за піксельний збіг з PNG)

- На десктопі компактний header + один hero; далі в «Огляд» перший рядок аналітики, нижче timeline та останні події.
- На 390px (та за потреби 320px) вкладки доступні раніше, ніж у baseline, немає окремого ряду лише для «Видалити».
- У «Книги» повноцінні дві колонки лише при достатній ширині, читабельні обкладинки, minibar для активної книги.
- «Історія» групується за локальними календарними днями, не виглядає як множина великих порожніх карточок.
- Навігація, aria, reduced motion і тема не погіршуються.

## Бекенд-дані / міграції

- Не переписувати історичний `book_counted.metadata.completedCount` без детермінованої реконструкції.
- Потрібен опис dry-run/тесту на старі записи; продакшен backfill потребує окремого контрольованого виконання. У звіті чітко вказати, чи старі записи тестового акаунта залишаються некоректними.
- Якщо `projected_late` змінює контракт — regenerate API-клієнт штатним процесом і перевірити всі exhaustiveness handling / уніфікацію локалізацій.

## Вимоги до завершального звіту Claude Code

1. Стислий changelog по етапах A–F (фактичні змінені файли).
2. Таблиця AC01–AC30 PASS / FAIL / BLOCKED із доказом (тест/скрін/посилання на код).
3. Виявлені блокери, недоробки та intentional deviations.
4. Підсумок фінальних перевірок та що саме запускалося (не стверджувати PASS без запуску).
5. Приклади скріншотів desktop/390px трьох вкладок, каталогу і модалки, якщо Chrome MCP доступний.
6. Окремий пункт: чи виправлені старі історичні event metadata, чи тільки нові, й чому.
7. Показати `git diff --stat`, active branch, commit SHA (без автоматичного merge у `dev`).

## QA-доповнення v3 — візуальні стани PNG

Перевірити наступні випадки окремо, не змінюючи production-дані та не створюючи нові цілі без дозволу:

- [ ] Порожній каталог цілей: `goal-first-goal-empty-state.png` видно, CTA доступний.
- [ ] Завершена ціль: `goal-completed-trophy-books.png`, коректні 100%, статус і дані.
- [ ] Низька/відсутня впевненість прогнозу: `goal-forecast-insufficient-data.png`, пояснення чому немає надійного прогнозу.
- [ ] Фільтр зарахованих книг порожній: `goal-no-counted-books-yet.png`, доступний шлях до всіх книг.
- [ ] Прострочена ціль: `goal-expired-hourglass.png` лише за статусу `expired` (не для активної цілі з пізнім прогнозом).
- [ ] Усі PNG зберігають прозорість, пропорції, не спричиняють layout shift/overflow на 390 px та desktop 100% zoom.
- [ ] Відповідні alt/декоративні alt не дублюють підписи, зображення не витісняють функціональні дії.

Якщо на тестовому акаунті немає стану, зафіксуй `NOT TESTED` і причину; не заявляй PASS без фактичної перевірки.
