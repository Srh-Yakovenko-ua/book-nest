# Book Nest · Фінальне шліфування цілей читання

Почни з актуальної `dev`. Аудит спирався на коміт `7aeb25f`. Звір вимоги з поточними компонентами й реалізуй лише відсутні зміни. Повторно використовуй компоненти, токени та ілюстрації Book Nest. Тексти додай для UK та EN.

## 1. Історія зарахувань

На dev у старій цілі «Прочитати 5 книг» дві різні події показують «1 із 5», хоча підсумок 2 із 5. ID цілі: `588e2d47-dc2a-4e42-9f58-d6f6ecb56eac`. Нові події дали правильні номери і при послідовному дочитуванні, і при зарахуванні двох книг під час створення нової цілі.

- Перевір чинний `apps/api/src/scripts/backfill-reading-goal-ordinals.ts`. За наявності доступу до dev виконай тільки `dry_run`. Використай точковий режим, якщо скрипт його підтримує. Інакше використовуй лише контрольоване середовище та звітуй окремо по цій цілі.
- Якщо послідовність відновлюється однозначно, зафіксуй запропоновані зміни та спосіб застосування. Запис у dev або prod потребує окремого дозволу. Якщо доступу бракує, продовж UI-зміни та вкажи, що перевірка історичних даних очікує доступу.
- Змінюй логіку запису лише за наявності відтворюваного бага на нових подіях. У такому разі додай один цільовий регресійний тест.

## 2. Створення цілі

- У формі, відкритій із каталогу, додай «Змінити список». Повернення відновлює пошук і фокус на виборі списку. Збережи чинне підтвердження виходу зі зміненої форми. Для прямого входу зі сторінки списку дію зміни джерела не показуй.
- Перед збереженням покажи кількість книг, які зарахуються одразу. Якщо цієї кількості досить для поточного порога, додай «Ціль одразу стане виконаною». Зі зміною порога оновлюй висновок. При нулі не показуй повідомлення. Використай авторитетні дані та чинні правила API, включно з часовим поясом користувача. Якщо бракує даних для точного підрахунку, отримай мінімальний read-only прогноз із повторним використанням серверної логіки. У стані помилки покажи загальне правило без непідтверджених чисел.
- Зарахування починається з календарного дня створення. Склад книг фіксується, кожна книга зараховується один раз, дедлайн включний. Створення наступної цілі після виконаної або простроченої зберігає чинне автоматичне архівування.

## 3. Деталі цілі

- Для активної цілі покажи одну основну дію біля прогресу. Якщо серед ще не зарахованих книг є та, яку зараз читають, «Продовжити читання» відкриває її. За кількох використовуй першу за чинним порядком списку. Інакше «Переглянути книги цілі» відкриває вкладку «Книги» з фільтром «Ще не зараховані». Незавантажені або неповні дані не трактуй як відсутність кандидата. Спочатку перевір, чи достатньо поточних даних деталей для вибору.
- Залиши факт і план на шкалі. Головну пораду сформулюй природно, наприклад «Щоб устигнути, дочитуй приблизно 1 книгу кожні 12 днів». Для коротких інтервалів і стану без прогнозу використовуй відповідні наявні формати. При відставанні не описуй його як частину книги в основному тексті.
- Додай явну дію «Усі цілі». Після переходу з каталогу відновлюй статус, сортування та вигляд. Пряме відкриття деталей веде в каталог із типовими налаштуваннями. Посилання на джерельний список лишається в метаданих.

## 4. Візуальне шліфування

- Для порожніх відфільтрованих результатів використай наявну ілюстрацію компактного розміру, орієнтовно 120–160 px. Заголовок і «Показати всі цілі» мають бути поруч із зображенням і видимими на типовому десктопі без окремого прокручування. Для «Архіву» та «Виконаних» додай конкретні заголовки «Архів порожній» і «Поки немає виконаних цілей». Великий порожній стан першої цілі збережи.
- Поясни, що означає знаменник успішності. Приклад підпису «0 із 2 цілей із підсумком». Перелік статусів у поясненні звір з фактичним розрахунком. Формулу не змінюй. Використай чинні PNG.

## Приймання

1. Один сценарій на ізольованих тестових даних. Створити ціль зі списку з двома книгами. Дочитати кожну. Перевірити 0% → 50% → 100% і окремі події 1 із 2, 2 із 2, «Ціль виконано». Створити наступну ціль того самого дня. Перевірити попередження перед збереженням, негайне групове зарахування й попередню ціль у «Архіві».
2. Один прохід із каталогу. Перевірити повернення до вибору із збереженим пошуком, обидві гілки основної дії в деталях та повернення до каталогу з фільтром. Коротко оглянути форму й порожній стан на мобільній ширині.
3. Запускай тільки цільові перевірки для змінених ділянок. Загальнопроєктні ESLint, typecheck і збірку залиш на фінал перед комітом, якщо їх вимагає репозиторій. Важкі команди запускай послідовно. У фіналі вкажи зміни, результати перевірок і статус `dry_run`.
