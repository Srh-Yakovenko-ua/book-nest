# Release to prod, 2026-09-27

Promotes `dev` onto `prod` (`de43a681`, released 2026-09-11). The exact promoted SHA is recorded on the promote PR.

## Delivery mechanics

Merging the promote PR pushes `prod`, which triggers `.github/workflows/deploy.yml`: build `:prod` images, push to GHCR, SSH to the box, `deploy.sh prod` (`compose pull`, `up -d`, health check, roll the image back if unhealthy). The api container runs `prisma migrate deploy` against the live prod database on boot via `apps/api/docker-entrypoint.sh`, so the five migrations below apply automatically on the first boot of the new image.

## Pre-flight (prod copy)

`pnpm db:copy:prod` dumped the live prod database read-only and loaded it into a throwaway local container on port 5434. `migrate deploy` then ran against that copy with `APP_ENV=prodcopy`, so `prisma.config.ts` loaded no env file and could not fall back to the local dev database. Prisma reported `injected env (0) from .env.prodcopy` and its datasource as `localhost:5434`.

- The live prod database was at 101 applied migrations, exactly the 101 in `prod`'s own tree
- `migrate status` listed the five migrations above as pending, and nothing else
- `migrate deploy` applied all five, exit 0
- `migrate status` afterwards reports "Database schema is up to date!" at 106
- Thirteen of thirteen hand-written indexes present afterwards
- Row counts across all 62 pre-existing tables were identical before and after. The only differences are the two new note tables at 0 rows each and five new `_prisma_migrations` rows
- Before the run, 0 tags had an unknown type, 6 timelines had a null color and 1 character existed (`major`). After it, the 6 timelines are `parchment`, `color_key` is not nullable, and the character's `importance_rank` is 1
- The copy container was removed afterwards, since it holds real user data

## Headline features

### Characters

- **A page per character.** A character opens on its own page instead of a side sheet, and editing happens there one section at a time. Adding a character goes through one dialog instead of two entry points. The whole cast of the library is on one page, and deleting a character now lists exactly what goes with it.
- **No spoilers from the cast.** Characters the reader has not reached, by reading position, disappear from the book roster, its counts and search, from contextual groups and theories, and from the series character views. What a character reveals before the reader gets there is chosen explicitly.
- **Per-book details.** A character's other names belong to the book they are used in, and the roster searches them. A book records who narrates it and where a character first shows up. An unspecified importance or status is told apart from a chosen one, which is what migrations 2 and 3 exist for: the roster now sorts by importance on the server through `importance_rank`.

### Genres, tags and publishers

- **Genres and tags split** into their own pages, and the genres page is served from paginated reads. The tags page shows the catalog as a grid or a list, sorts newest first and has redesigned structure and usage blocks.
- **Tag colors everywhere.** Every tag renders in its own color in the book form and in the tag filters, the way the tags page does. Timelines and tags now share one eight-color palette defined once in `packages/shared`.
- **Publishers rebuilt.** A new archive and publisher page on extended contracts, a lighter grid card and a tidied sidebar.

### Lists

- **Quick filter counts.** Every quick filter chip on the library, loans, dedications, in-transit deliveries and publishers pages counts what it would show under the current search, taken from dedicated quick-count reads. What a count means is written down in `docs/`. Chips keep a stable width while counts load.
- **Endless scroll.** Sixteen page-level lists fetch the next page as the reader nears the end instead of waiting for "load more". A failed page stops auto-loading and shows a retry button, and eleven views no longer replace the whole loaded list with an error when only page two failed.
- **Facet filters show their selection.** A selected value shows its name, appears as a removable chip and sorts first.

### Book timeline

Events gain a spoiler flag, and a flagged event hides the same way as an event past the reader's page, in the stream, the list and the detail dialog. The overview covers the whole book and its cards drill into a clean filter state. The event form is rebuilt from collapsible sections, and following a relation stays inside one dialog. This is migration 5.

### Notes and books

- **Notes that come back.** A rediscovery block and an after-finishing recap on the book notes page, and a "before you continue the series" block on the series notes page, backed by the two tables in migration 1.
- **Book form.** A new book in a series gets the series publisher suggested and its genres prefilled. Saving the edit form no longer wipes the page count or the delivery price of a book in transit: `setValueAs` turned the saved number into null before anyone touched the field.

## Runbook

1. Pre-flight against a prod copy (above), green.
2. Commit-tree promotion: tree of `dev`, parent `origin/prod`, pushed as `promote-prod`, PR into `prod`.
3. The prod PR runs the CI gate (`static`, `test-api` four-way shard, `test-web`, `build` plus API smoke against a `migrate deploy`'d empty database, then the `CI gate` fan-in).
4. Squash-merge, `prod` push, deploy workflow, migrations auto-apply on api boot.
5. Verify `https://book-nest.net/api/health` returns `"status":"ok"` with a fresh uptime, that a new route answers 401 rather than 404, and that the What's New feed carries 107 entries.

### Rollback

`deploy.sh` rolls the image back automatically if the container never turns healthy. It does not roll migrations back, and this time that matters.

Migrations 1 to 4 are safe under the previous image: new tables it never reads, a column with a default, a default change and a no-op update. Migration 5 is not. The previous image validates `color_key` against the old twelve-key enum when it builds the timeline overview, so a `parchment` value throws there, and it creates a timeline with `colorKey: null`, which the new `NOT NULL` rejects. If the new image fails to boot after the migrations ran, the old image serves everything except timelines. Timelines stay broken until the new image is fixed forward, since reverting the palette would need a hand-written reverse mapping.

Prod has no automated backups. A fresh `pg_dump` of prod taken for this pre-flight is kept on the release machine until the deploy is verified, as the only restore point.
