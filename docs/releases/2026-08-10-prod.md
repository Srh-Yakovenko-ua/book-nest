# Release to prod, 2026-08-10

Promotes `dev` onto `prod` (`a217bfe4`, released 2026-08-07). The exact promoted SHA is recorded on the promote PR.

## Delivery mechanics

Merging the promote PR pushes `prod`, which triggers `.github/workflows/deploy.yml`: build `:prod` images, push to GHCR, SSH to the box, `deploy.sh prod` (`compose pull`, `up -d`, health-check, roll the image back if unhealthy). The api container runs `prisma migrate deploy` against the live prod database on boot via `apps/api/docker-entrypoint.sh`, so the four migrations below apply automatically on the first boot of the new image.

## Pre-flight (prod copy)

`pnpm db:copy:prod` dumps the live prod database read-only and loads it into a throwaway local container, then `migrate deploy` runs against real data.

- All four migrations applied, `migrate deploy` exit 0
- Ten of ten raw-SQL indexes present afterwards, eight of them still partial
- Copy container and dump removed afterwards, since they hold real user data

Row counts on real prod data:

| Table                            | Before | After |
| -------------------------------- | ------ | ----- |
| `book_purchase_info`             | 79     | 4     |
| `book_store_links`               | 0      | 37    |
| `books` with `wishlist_added_at` | 0      | 40    |

The drop from 79 to 4 looks alarming and is not. Parsing the pre-migration dump row by row accounts for every deleted row:

- 37 rows carried a store url. All 37 became links, so 37 in and 37 out with nothing lost. Their store columns were then cleared and the rows deleted as empty.
- 38 rows were already completely empty before the migration ran, with all five content fields null. They recorded nothing and were deleted as such.
- 37 + 38 = 75 deleted, leaving the 4 survivors: three rows holding a price with no shop, and one holding a stray currency.

No row carried a note and none was marked purchased, so nothing of value was in the deleted set. The 40 books on the wishlist all received an entry date, matching the wishlist size exactly.

## Headline features

- **Reading goals.** A new feature end to end, with a new route at `/goals/[id]`. Set a goal to read a number of books from one of your lists by a date, see progress on a card on the list itself, and open a page listing the books that count toward it. Status is computed as you read rather than stored. Goals can be edited, archived or deleted, and a list holds at most one open goal, enforced by the partial unique index in migration 3 so archiving frees the slot.
- **The list details page, rebuilt.** A sidebar with what the list is about, what you are currently reading from it, related lists and summary numbers. Quick tabs and advanced filters that show how many books sit behind each value before you pick it. Drag and drop ordering, multi-select with bulk actions including bulk removal, whole-list duplication, and a per-book menu with the next sensible step. 29 new files under `apps/web/src/features/lists`.
- **Wishlist entry dates and counts.** `books.wishlist_added_at` is stamped when a book enters the wishlist and cleared when it leaves, across all seven code paths that write an ownership status. The summary endpoint gained four counts: added in the last 30 days, waiting over six months, and books that are either the next part or a gap in a series the reader already owns part of.
- **Wishlist store links, completed.** The shop and price entered when adding a book now land where the wishlist reads them. Migrations 1 and 2 move the rows written under the old path and remove the duplicate, so `book_store_links` becomes the single answer to where a book can be bought.
- **Wishlist ownership cleanup.** Books carrying no ownership status are sorted out rather than silently grouped with wanted ones, and catalog filtering for lists moved to the server.

1. Pre-flight against a prod copy (above), green.
2. Commit-tree promotion: tree of `origin/dev`, parent `origin/prod`, pushed as `promote-prod`, PR into `prod`.
3. The prod PR runs the CI gate (`static`, `test-api` four-way shard, `test-web`, `build` plus API smoke against a `migrate deploy`'d empty database, then the `CI gate` fan-in).
4. Squash-merge, `prod` push, deploy workflow, migrations auto-apply on api boot.
5. Verify `https://book-nest.net/api/health` returns `"status":"ok"`.

### Rollback

`deploy.sh` rolls the image back automatically if the container never turns healthy. It does not roll migrations back, and this release is where that distinction matters most.

Migrations 3 and 4 are forgiving under a rolled-back image. Prisma never issues `SELECT *`, it expands an explicit column list from the fields the generated client knows about, so the old image simply never asks for `wishlist_added_at` and never sees `reading_goals`. Both are additive and the previous code runs against the migrated schema unchanged.

Migrations 1 and 2 are not reversible by rolling back the image, because they moved data rather than changing shape. If the new image failed to boot after they applied, the old code would read `book_purchase_info` and find the store fields cleared, so a wanted book would show no shop even though the link exists in `book_store_links`. Recovering means rolling forward, not back: deploy a working image rather than reverting one. The pre-flight is what makes that acceptable, since it ran both migrations against a copy of exactly this data and the result was accounted for row by row.
