# Release to prod, 2026-09-11

Promotes `dev` onto `prod` (`5f687478`, released 2026-09-06). The exact promoted SHA is recorded on the promote PR.

## Delivery mechanics

Merging the promote PR pushes `prod`, which triggers `.github/workflows/deploy.yml`: build `:prod` images, push to GHCR, SSH to the box, `deploy.sh prod` (`compose pull`, `up -d`, health check, roll the image back if unhealthy). The api container runs `prisma migrate deploy` against the live prod database on boot via `apps/api/docker-entrypoint.sh`, so the two migrations below apply automatically on the first boot of the new image.

## Pending migrations

| #   | Migration                                          | Risk     | Notes                                                                                                                                                          |
| --- | -------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `20260910140033_add_quote_rediscovery_impressions` | **SAFE** | New table `quote_rediscovery_impressions`. Two plain indexes, one unique index on `(user_id, quote_id, shown_on)`, cascading FKs to `users` and `quotes`.      |
| 2   | `20260910151736_add_quote_post_finish_reviews`     | **SAFE** | New table `quote_post_finish_reviews`. One plain index, one unique index on `(user_id, reading_cycle_id)`, cascading FKs to `users` and `book_reading_cycles`. |

Both migrations are `CREATE TABLE` plus indexes and foreign keys on the table they just created. No existing column changes and nothing is dropped. Both unique indexes are built on tables that are empty at that moment, so there is no existing data for them to reject. They exist to make the two tracking writes idempotent: recording the same impression twice on one day, or reviewing the same reading cycle twice, collides instead of adding a second row.

Adding a foreign key briefly locks the referenced table (`users`, `quotes`, `book_reading_cycles`) against writes while Postgres checks the referencing rows. The referencing table is empty, so the check is over as soon as it starts.

### Raw-SQL index strip-trap

Clean. There is no `DROP INDEX` anywhere in the release, and neither migration adds a hand-written index, so the set stays at thirteen. All thirteen were confirmed present on the migrated prod copy.

## Pre-flight (prod copy)

`pnpm db:copy:prod` dumped the live prod database read-only and loaded it into a throwaway local container on port 5434. `migrate deploy` then ran against that copy with `APP_ENV=prodcopy`, so `prisma.config.ts` loaded no env file and could not quietly fall back to the local dev database. Prisma reported its datasource as `localhost:5434` on every call.

- The live prod database was at 99 applied migrations, none failed or rolled back, exactly the 99 in `prod`'s own tree
- `migrate status` listed the two migrations above as pending, and nothing else
- `migrate deploy` applied both, exit 0
- `migrate status` afterwards reports "Database schema is up to date!" at 101
- Thirteen of thirteen hand-written indexes present afterwards
- Row counts across all 60 pre-existing tables were identical before and after. The only differences are the two new tables, at 0 rows each, and two new `_prisma_migrations` rows
- Copy container and dump removed afterwards, since they hold real user data

## Headline features

### Quotes

- **Filters that tell you what they will find.** The single book picker became a Filters sheet with multi-selects for books and authors and a date-added range, and every quick filter now carries a count. All of it comes from one new request, `GET /api/quotes/facets`, which builds its numbers with the same where-builder as the list, so the counts and the list cannot drift apart. Each facet answers to every active filter except its own, which keeps an empty combination recoverable. Old links with a `bookId` still land on a filtered list.
- **Four overview cards.** How many books you quote from, how many quotes a quoted book gets on average, the most quoted book and the most quoted author. The author comes from the book's author relation rather than the free-text first author, so a quote from a two-author book counts for both. When several books or authors share the top count, the summary returns how many share it and no name, instead of presenting whichever row Postgres returned first as the winner.
- **Quotes that come back.** One quote a day from the reader's own archive, chosen from quotes saved at least 30 days ago, and for 30 days after finishing a book a recap of the quotes collected from it. Selection is deterministic per user per day, favours favourites and commented quotes, keeps a cooldown and never offers a spoiler. All of that lives on the server behind `GET /api/quotes/overview`; the page renders what it is given. An impression is recorded only when the block is actually on screen, because the desktop sidebar is hidden by CSS on phones and would otherwise report views nobody saw. The two new tables hold those impressions and reviews.
- **A calmer archive.** The card became a preview: the quote fills the space the card has left, and long text or a spoiler opens a dialog. Grid cards share one height from the md breakpoint up, the list gained a grid/list switch and a "show more" button in place of numbered pages, and the sort menu stopped offering favourites and spoilers, which the filter chips already cover.

### Spending statistics

- **Purchase dynamics.** The chart and an insights card now sit side by side, and the insights card chooses its rows instead of rendering whatever arrived, so it is never blank. The tooltip's percent change was wrong: the chart divided by a hundred before a formatter that expects a value already in percent, so growth of 5206% read as 52.1%. That is fixed and covered by a test.
- **Where the price comes from.** The cost block reads as a bridge from the starting price through discounts, delivery and the order-total residual to the actual cost. The delivery and discount cards show orders, cost per book and shares underneath, and a metric whose denominator the API reports as unknown drops out rather than showing a made-up number.
- **Stores.** Ranking and comparison are one section. The best value store gets a crown, the ranking pages by five, and the scatter compares book price with average order value. Hover and selection are separate state now, which is what makes the drill-down under the chart reachable: it used to vanish the moment the pointer left the point on its way to the link. The points are focusable and selectable from the keyboard.
- **Purchase calendar.** A new `calendarCoverage` field in the statistics contract lets the calendar say how many orders it left out for lack of an order date, instead of the page guessing from a difference of totals. The three empty cases are told apart, and shading follows the spread of active days, so one busy day no longer washes out every other day.
- **Records.** Records read their own projection with cancelled orders and items removed, so a cancelled order can no longer win one. Each category returns up to three equal winners, decided once on the backend. Money is compared in minor units, because summing floats made two genuinely equal months differ by a fraction of a cent and the tie was missed. The record for most books bought in one store was computed all along and is now shown.
- **Delivery bars.** Both delivery blocks drew their bars against the fullest row, so the widest bar always filled its track while the number beside it said something else. Bars are now measured against the total the backend reports.

### Search

Deleting a search down to one character left the previous query running, so the field showed "к" while the list was still filtered by "кн". A draft too short to search now clears the search. Searches that start from the first character, like the library's ISBN lookup, are untouched.

## Runbook

1. Pre-flight against a prod copy (above), green.
2. Commit-tree promotion: tree of `dev`, parent `origin/prod`, pushed as `promote-prod`, PR into `prod`.
3. The prod PR runs the CI gate (`static`, `test-api` four-way shard, `test-web`, `build` plus API smoke against a `migrate deploy`'d empty database, then the `CI gate` fan-in).
4. Squash-merge, `prod` push, deploy workflow, migrations auto-apply on api boot.
5. Verify `https://book-nest.net/api/health` returns `"status":"ok"` with a fresh uptime, that `GET /api/quotes/overview` exists (401 without a token rather than 404), and that the What's New feed carries the new entries.

### Rollback

`deploy.sh` rolls the image back automatically if the container never turns healthy. It does not roll migrations back, and for this release it does not need to.

Both migrations are additive, so the previous image runs unchanged against the migrated schema. Prisma always expands an explicit column list from the fields its generated client knows, so the old image never asks about the two new tables. The cascades are enforced by Postgres itself, which means a hard delete of a quote, a user or a reading cycle issued by the old image still removes the matching impression and review rows without that image knowing they exist. If the new image fails to boot, the old one serves correctly on the new schema, and the only loss is the quotes sidebar blocks.
