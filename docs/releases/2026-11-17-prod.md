# Release to prod, 2026-11-17

Promotes `dev` onto `prod` (`7bddd33f`, released 2026-10-19). The exact promoted SHA is recorded on the promote PR.

## Delivery mechanics

Merging the promote PR pushes `prod`, which triggers `.github/workflows/deploy.yml`: build `:prod` images, push to GHCR, SSH to the box, `deploy.sh prod` (`compose pull`, `up -d`, health check, roll the image back if unhealthy). The api container runs `prisma migrate deploy` against the live prod database on boot via `apps/api/docker-entrypoint.sh`, so the four migrations below apply automatically on the first boot of the new image.

`prod`'s tree is byte-identical to dev commit `014e254f` ("docs(releases): notes for the 2026-10-19 prod release"), so everything new is `014e254f..dev`. The counts below cover `014e254f..c30f0b48`, the last merge before the two release commits (changelog entries and these notes):

## Headline features

### Statistics

- **Reading calendar page.** The reading calendar moved to `/reading-calendar`, opened from the heatmap, with the books-by-day view reworked and long calendars paged a year at a time.
- **Activity tab.** Rebuilt around dynamics, habits and weekdays.
- **Tastes and Progress.** Each taste ranking row opens the exact finished reads behind it, and both tabs say what each number counts.

### Characters and relationships

- **Book-first relationships.** A relationship is created from the book, and custom relationship types and role labels go into a personal dictionary that is suggested next time. This is migrations 2 and 3.
- **Relationship map.** A book's relationship graph has its own page with around-a-character, family tree and whole network views and a shortest-path walk.
- **Catalog.** Character cards show the books each character appears in, and the filter sheet shows facet counts. The separate `favorite` attitude is gone, the heart already marks favorites. This is migration 1.

### Reader time zone

Goal, loan, book, reading queue, delivery and statistics days are counted in the time zone from the reader's profile instead of the server's, weeks start on the reader's week start, and the time zone picker finds and saves current zone names. Typed delivery and return days saved earlier at UTC midnight move to the start of the same day in the reader's zone. This is migration 4.

### Errors and sessions

Loaded data stays on screen when a refresh fails, failed sections show on their own with a retry, error pages are translated, and the focus ring is visible. Signing out or switching accounts clears the previous user's cached data, screen state and drafts, and a request is never resent under another user's session.

## Runbook

1. Pre-flight against a prod copy (above), green.
2. Commit-tree promotion: tree of `dev`, parent `origin/prod`, pushed as `promote-prod`, PR into `prod`.
3. The prod PR runs the CI gate (`static`, `test-api` four-way shard, `test-web` three-way shard, `build` plus API smoke against a `migrate deploy`'d empty database, then the `CI gate` fan-in).
4. Fresh read-only `pg_dump` of prod right before the merge, kept as the restore point.
5. Squash-merge, `prod` push, deploy workflow, migrations auto-apply on api boot.
6. Verify `https://book-nest.net/api/health` returns `"status":"ok"` with a fresh uptime, and that the What's New feed carries 135 entries.

### Rollback

`deploy.sh` rolls the image back automatically if the container never turns healthy. It does not roll migrations back. Both paths were rehearsed on the migrated prod copy with the previous release's migrations folder and schema (`014e254f`):

- **Image rollback after the migrations applied.** The previous image's `migrate deploy` finds its 113 migrations, reports "No pending migrations to apply" and exits 0, so it boots over the four it does not know. On current prod data none of the four rewrote a row, so the previous code reads exactly what it read before.
- **A migration that fails or is killed halfway.** Prisma leaves its row in `_prisma_migrations` with `finished_at` null. The previous image then stops on `P3009 migrate found failed migrations` and the api crash-loops. `prisma migrate resolve --rolled-back <migration name>` clears it, and the previous image's `migrate deploy` exits 0 afterwards. Migrations 2 and 3 set no `lock_timeout`, so a session left `idle in transaction` on `users` or `character_relationships` is the realistic way to hit this; right before the merge prod is checked read-only for such sessions and for unfinished migration rows.

Two notes for a rollback that lasts long enough for readers to write data under the previous image. The previous image still accepts the `favorite` attitude, and the new code rejects it when parsing, so rerun migration 1's two `UPDATE` statements as a new migration before re-releasing. The previous image reads a loan's return day as its UTC date and saves typed days at UTC midnight, so rerun migration 4's three `UPDATE` statements the same way; they are idempotent.

Prod has no automated backups. The `pg_dump` taken in step 4, `/tmp/booknest_prod_dump.sql` on the release machine, is the only restore point and is kept until the deploy is verified.
