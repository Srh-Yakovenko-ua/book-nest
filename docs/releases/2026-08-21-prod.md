# Release to prod, 2026-08-21

Promotes `dev` onto `prod` (`189b3831`, released 2026-08-10). The exact promoted SHA is recorded on the promote PR.

## Delivery mechanics

Merging the promote PR pushes `prod`, which triggers `.github/workflows/deploy.yml`: build `:prod` images, push to GHCR, SSH to the box, `deploy.sh prod` (`compose pull`, `up -d`, health-check, roll the image back if unhealthy). The api container runs `prisma migrate deploy` against the live prod database on boot via `apps/api/docker-entrypoint.sh`, so the fourteen migrations below apply automatically on the first boot of the new image.

## Scope

`git log origin/prod..origin/dev` reports a number in the hundreds. That number measures the branch model, not the release. `prod` carries a linear chain of squash commits while `dev` carries real history, so their merge-base is ancient and the range re-counts almost all of dev.

The real delta is verifiable by tree. `prod`'s tree is byte-identical to dev commit `1d09f909` ("docs(releases): notes for the 2026-08-10 prod release"), so everything new is `1d09f909..origin/dev`:

- 174 commits (127 non-merge), 43 merged PRs: #106 through #148
- 1442 files, +136752 / -17188: 981 web, 397 api, 40 docs, 21 shared, plus `CLAUDE.md`, `.prettierignore` and one `.claude` file

Migrations 4 and 10 are the pair that needed proving rather than reasoning about. Together they retire `book_deliveries` in favour of orders, items and shipments, and a drop of a table holding real rows would be unrecoverable. The pre-flight below proves the table is empty on prod, which turns the whole conversion into a schema change.

Migration 12 is the other one worth naming. `SET NOT NULL` fails loudly rather than silently if a single loan is left without a contact, so its safety rests entirely on the backfill in migration 11 covering every row. The pre-flight shows it does.

### Raw-SQL index strip-trap

Clean. The only `DROP INDEX` in the release is migration 9, which replaces a plain index it also declared. No trigram GIN index and no partial index is dropped anywhere. Migration 14 adds one hand-written partial unique index, `book_budgets_active_currency_idx`, and migration 3 adds `book_order_items_active_book_idx`, bringing the hand-written set to twelve. All twelve were confirmed present on the migrated prod copy with their predicates intact.

## Pre-flight (prod copy)

`pnpm db:copy:prod` dumps the live prod database read-only and loads it into a throwaway local container on port 5434, then `migrate deploy` runs against real data.

- All 14 migrations applied, `migrate deploy` exit 0, `migrate status` reports the schema up to date at 96 migrations
- Twelve of twelve hand-written indexes present afterwards, ten of them still partial
- Copy container and dump removed afterwards, since they hold real user data

Row counts on real prod data, before and after. Of the 52 tables in the dump, 50 kept their exact count. `_prisma_migrations` grew from 82 rows to 96 as the migrations recorded themselves, and `book_deliveries` was dropped while empty. Seven new tables arrived, one of them with a row:

The one row the release writes to prod data is the loan contact. All five existing loans name the same person with no contact details, so the backfill collapses them into a single `loan_contacts` row and points all five loans at it. Afterwards no loan is left without a contact, which is what lets migration 12 add the NOT NULL.

## Headline features

- **Orders and parcels.** A delivery is no longer one book travelling alone. An order holds several books, splits into parcels, and is managed from its card: money, order date and note are editable, a single book carries its own price, a parcel changes status in one click or is received from its menu. Three new tables and the retirement of `book_deliveries` sit under this.
- **The books in transit page, rebuilt.** Five quick filters instead of a crowd, reworked stat cards, a sidebar with the next delivery, a block naming the deliveries that need something from you, a block saying what the library gains once the parcels land, advanced filters, and bulk receiving by parcel.
- **The order history, rebuilt.** Grouped into orders, parcels and books, with its own sidebar per tab, the same advanced filter sheet the active list uses, and a cancelled tab that says both what a cancelled book still needs and where the rest of them ended up.
- **Order statistics and a monthly budget.** The statistics page became a decision dashboard: a period with an optional comparison, four headline numbers, where the money goes once delivery and discounts are counted, where orders are stuck and for how long, which store is the better deal, and which month cost the most. Every amount keeps UAH, EUR and USD on separate scales, nothing is summed across currencies, and most of the page links back into the filtered lists. A monthly budget per currency is stored as a version history, so a finished month keeps the budget it was judged against.
- **Loans, rebuilt around people.** Lent and borrowed each got stat cards, a sidebar and quick filters, a loan card with quick actions and its own reminder schedule, a full history page with corrections, and a contacts page: the person is now the one place a contact lives, their card opens from every place their name appears, and a loan can start from the person rather than the book.
- **Reading goals on a book snapshot.** A goal now records the books it counts at the moment it is created, so editing the list underneath no longer rewrites history, and a goal activity log records what happened to it.
- **Facet filters everywhere.** Filters across the book pages show how many books stand behind each value before you pick it, and the series list filters and sorts on the server rather than on the page in front of you.

1. Pre-flight against a prod copy (above), green.
2. Commit-tree promotion: tree of `origin/dev`, parent `origin/prod`, pushed as `promote-prod`, PR into `prod`.
3. The prod PR runs the CI gate (`static`, `test-api` four-way shard, `test-web`, `build` plus API smoke against a `migrate deploy`'d empty database, then the `CI gate` fan-in).
4. Squash-merge, `prod` push, deploy workflow, migrations auto-apply on api boot.
5. Verify `https://book-nest.net/api/health` returns `"status":"ok"` and that the What's New feed carries the new entries.

### Rollback

`deploy.sh` rolls the image back automatically if the container never turns healthy. It does not roll migrations back.

Most of this release is forgiving under a rolled-back image. Prisma never issues `SELECT *`, it expands an explicit column list from the fields the generated client knows about, so the old image simply never asks for `is_free`, `remind_before_days` or `loan_contact_id` and never sees the seven new tables. Migrations 2, 3, 5, 8, 13 and 14 are additive in that sense and the previous code runs against the migrated schema unchanged.

Three are not reversible by rolling the image back.

Migration 1 changes how text sorts. Old code reading a migrated database returns rows in Ukrainian collation order, which is a different order than it used to return but never a wrong answer, so this one is only cosmetic under a rollback.

Migration 10 drops `book_deliveries`, and the old image still queries it. If the new image failed to boot after migration 10 applied, the delivery endpoints of the old image would fail on a missing relation. Recovering means rolling forward, deploying a working image, rather than reverting one. The pre-flight is what makes that acceptable: the table is empty, so nothing of the reader's is inside it.

Migration 12 makes `book_loans.loan_contact_id` mandatory. The old image writes loans without it and every such insert would fail. Same conclusion: roll forward, not back.

The practical reading is that the window where a rollback helps closes at migration 10. Before it, the old image runs fine on the new schema. After it, the fix is a working image, and the pre-flight is what makes that a controlled risk rather than a gamble.
