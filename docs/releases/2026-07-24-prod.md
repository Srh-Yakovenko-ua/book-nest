## Delivery mechanics (how this actually ships)

- Deploy triggers on **push to `dev` or `prod`** (`.github/workflows/deploy.yml`).
  Merging this PR into `prod` pushes `prod` → the deploy workflow builds the `:prod`
  images → SSH-deploys to the box (`deploy@46.224.83.71`) → `deploy.sh prod` does
  `docker compose pull → up -d → health-check → rollback-image-on-unhealthy`.
- On boot the api image entrypoint (`apps/api/docker-entrypoint.sh`) runs
  **`prisma migrate deploy` against the live prod DB on container start**, then the
  seed scripts, then boots. There is **no separate manual migration gate** — pushing
  to `prod` auto-applies every pending migration to the prod database.
- If a migration fails on real data, `migrate deploy` exits non-zero → entrypoint
  `set -e` → container never becomes healthy → `deploy.sh` rolls back the _image_.
  The image rollback does **not** roll back already-applied migrations, so a
  data-dependent failure can leave the DB partially migrated under the old image.
  This is why the prod-copy pre-flight below is mandatory even though the batch is
  fully additive.

## Deploy runbook

1. **CI gate**: the direct `dev → prod` commit-tree PR runs the `full` job (build +
   `migrate deploy` on an empty ephemeral Postgres + tests + API smoke) plus `static`
   (typecheck + lint). Must be green before merge. (apps/web Storybook headless flake is
   a known non-blocker — re-run once if it trips, distinguish from a real failure.)
2. **DB pre-flight on a prod copy** — done this session, GREEN (see above). This is the
   step that catches data-dependent failures the empty-DB CI cannot.
3. **Promote to prod**: merge the commit-tree PR (squash). The push to `prod` builds the
   `:prod` images and SSH-deploys; the api container auto-runs `migrate deploy` on the
   live prod DB on boot.
4. **Verify**: `curl -fsS https://book-nest.net/api/health` → `"status":"ok"` (the deploy
   workflow also gates on this), then a smoke of a couple of new endpoints if relevant.

## Rollback

- Migrations are additive (new tables, defaulted bool columns, index reshaping), so old
  code tolerates the new schema — a code rollback (redeploy the previous `:prod` image) is
  safe without a DB downgrade. There is no down-migration; recovery from a bad migration is
  a forward fix. Dropping the redundant `*_user_id_idx` indexes is likewise non-destructive
  to data and reversible by re-creating them.
