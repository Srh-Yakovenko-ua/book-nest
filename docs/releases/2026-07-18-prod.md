`prod..dev` git delta and the pending Prisma migration set. The **authoritative**

## Delivery mechanics (how this actually ships)

- Deploy triggers on **push to `dev` or `prod`** (`.github/workflows/deploy.yml`).
  `stage` is **not** a runtime env — it is the CI gate (the `full` job runs on PRs
  whose base is `stage`/`prod`: build + `migrate deploy` against an _empty_ ephemeral
  Postgres + tests + API smoke).
- On a prod deploy the api image entrypoint (`apps/api/docker-entrypoint.sh`) runs
  **`prisma migrate deploy` against the live prod DB on container start**, then the
  seed scripts, then boots. There is **no separate manual migration gate** — pushing
  to `prod` auto-applies every pending migration to the prod database.
- If a migration fails on real data, `migrate deploy` exits non-zero → entrypoint
  `set -e` → container never becomes healthy → `deploy.sh` rolls back the _image_.
  The image rollback does **not** roll back already-applied migrations, so a
  data-dependent failure can leave the DB partially migrated under the old image.
  This is why the prod-data pre-flight below matters even though the batch is additive.

## Deploy runbook

1. **Confirm the real delta**: on the server, `prisma migrate status` against the prod DB
   — verify the pending list matches the table above (guards against a stale local ref).
2. **CI gate**: open a PR with base `stage` (or `prod`) so the `full` CI job runs
   (build + migrate-on-empty + tests + smoke). Must be green.
3. **DB pre-flight on a scratch copy of prod** (the risky step, done off the live DB):
   - `pg_dump` the prod DB → restore into a throwaway DB (local docker or a scratch DB
     on the server, **never** the live prod DB).
   - Run `pnpm --filter @app/api db:migrate:deploy` against that scratch DB.
   - Confirm all 10 apply cleanly and the seed scripts run. Spot-check row counts.
4. **Promote to prod** (per the branch model: `release/prod` commit-tree promotion —
   mind the squash add/add conflict trap). The push to `prod` builds `:prod` images and
   SSH-deploys; the api container auto-runs `migrate deploy` on the live prod DB on boot.
5. **Verify**: `curl -fsS https://book-nest.net/api/health` → `"status":"ok"` (the deploy
   workflow already gates on this), then a smoke of a couple of new endpoints.

## Rollback

- Migrations are additive (new tables + nullable/defaulted columns), so old code tolerates
  the new schema — a code rollback (redeploy previous `:prod` image) is safe without a DB
  downgrade. There is no down-migration; recovery from a bad migration is a forward fix.
