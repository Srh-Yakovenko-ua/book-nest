## Pending migrations

| #   | Migration                                  | Risk     | Notes                                                                                                                                                           |
| --- | ------------------------------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `20260806132833_media_reference_no_action` | **SAFE** | Drops and re-adds four FKs pointing at `media_assets`, flipping `ON DELETE` from `SET NULL` to `NO ACTION`. No column, table or index changes. No data rewrite. |

The four constraints: `books_cover_media_id_fkey`, `characters_avatar_media_id_fkey`, `character_forms_portrait_media_id_fkey`, `book_characters_portrait_media_id_fkey`.

Why it is SAFE rather than RISK: an `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY` validates existing rows, so it fails if any referencing row points at a missing `media_assets` id. The pre-flight proved there are zero such rows on real prod data (below), so the validation pass is a no-op. Nothing is dropped, no column is narrowed, no unique index is introduced.

`NO ACTION` rather than `RESTRICT` is deliberate: deleting a user cascades books and media in one statement, and `RESTRICT` fires on the intermediate state where the media row is gone but the book row has not been reaped yet. `NO ACTION` defers the check to the end of the statement, so the cascade still works.

### Raw-SQL index strip-trap

Clean. The migration contains no `DROP INDEX` at all, so none of the nine hand-written raw-SQL indexes are touched. Nothing to hand-strip.

## Behaviour change this migration ships (verified in code)

Before: `media_assets` rows could be deleted while a book still pointed at them, and Postgres would silently null out `books.cover_media_id`. A book quietly lost its cover, and the blob was gone from object storage unrecoverably.

After: the delete raises Postgres `23503` (foreign key violation), which Prisma surfaces as `P2003`.

Confirmed the API handles that rather than leaking a 500 — the chain is closed end to end:

- `apps/api/src/core/prisma-errors.ts` — `isForeignKeyConstraintError` matches `PrismaClientKnownRequestError` with code `P2003`.
- `apps/api/src/modules/media/application/media.service.ts` — `removeAssetIfUnreferenced` wraps `mediaRepository.deleteOwned` in try/catch, returns `false` on `isForeignKeyConstraintError(error)`, and rethrows anything else. Because the check and the delete are now one atomic statement, the old count-then-delete race is gone.
- Same file, `delete()` — on `false` throws `ConflictError("Media is still in use", { code: MEDIA_ERROR_CODES.stillReferenced })`.
- `apps/api/src/core/exceptions/errors.ts` — `ConflictError` carries `HTTP_STATUS.CONFLICT`, so `DELETE /api/media/:id` answers **409** with code `MEDIA_STILL_REFERENCED`, documented via `@ApiConflictResponse` on the controller.
- `deleteIfUnreferenced()` (the cleanup path used by `BookCoverCleanup`) ignores the `false` and leaves the asset in place, so cover replacement does not throw.

No frontend impact: `DELETE /api/media/:id` has no caller in `apps/web`, which is why this is not in the what's-new feed.

### Rollback

`deploy.sh` rolls the **image** back automatically if the container never turns healthy. It does not roll migrations back. This migration is unusually forgiving there: it only changes FK delete behaviour, adds no column and drops nothing, so the previous image runs against the migrated schema with no schema conflict. The only behavioural difference under a rolled-back image is that `DELETE /api/media/:id` on a referenced asset would return 500 instead of 409, since the old code has no `P2003` branch. That endpoint has no frontend caller, so user impact is nil.

If a manual revert is ever needed, it is a one-liner per constraint: drop and re-add with `ON DELETE SET NULL`.
