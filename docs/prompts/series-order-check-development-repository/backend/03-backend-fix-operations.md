# Backend: операції виправлення

## Загальне правило

Кожна операція має дві фази:

```text
preview → явне підтвердження → apply
```

Backend є джерелом істини для обох фаз.

## 1. `ADD_NEXT_PREVIOUS_BEFORE`

Використовується, коли першої актуальної попередньої книги немає в черзі.

### Приклад

Було:

```text
1 A
2 B
3 C
4 Книга 3
5 D
```

Стало:

```text
1 A
2 B
3 C
4 Книга 2
5 Книга 3
6 D
```

### Перевірки

- книга ще не в черзі;
- проблемна книга все ще в черзі;
- series relationship не змінився;
- reading status все ще незакритий;
- queue limit не перевищено;
- user має доступ;
- queue version актуальна.

## 2. `ADD_ALL_PREVIOUS_BEFORE`

Додає всі відсутні незакриті книги перед проблемною книгою у канонічному порядку.

### Приклад

```text
Буде додано:
- Книга 2
- Книга 3

Перед:
- Книга 4
```

Операція застосовується лише повністю. Якщо хоча б одну книгу неможливо додати або перевищено ліміт, не додавати жодної.

## 3. `REORDER_SERIES_SLOTS`

Рекомендована стратегія для книг серії, які вже є в черзі.

Переставляються лише книги цієї серії в позиціях, які вони вже займають.

Було:

```text
2 — Книга 3
3 — Соло A
4 — Книга 2
5 — Соло B
```

Стало:

```text
2 — Книга 2
3 — Соло A
4 — Книга 3
5 — Соло B
```

Сторонні книги залишаються на тих самих queue positions.

## 4. `previous_book_paused`

Sidebar не виконує queue fix автоматично.

Дозволені варіанти:

- відкрити книгу;
- викликати чинний resume flow, якщо він уже є;
- після mutation reading status виконати refetch issues.

Не створювати нову складну атомарну зміну current reading, якщо такої операції немає в домені.

## 5. `current_reading_ahead_of_order`

Не можна автоматично:

- зупиняти активне читання;
- переносити reading progress;
- ставити пізнішу книгу на паузу;
- починати попередню книгу.

Дія відкриває попередню книгу. Issue існує, доки користувач сам не змінить статус або не проігнорує конфлікт.

## 6. Ownership-related flows

### `NONE`

Перевикористати mutation `NONE → WANT_TO_BUY`. Це не є queue fix і не гарантує зникнення issue.

### `WANT_TO_BUY`

Відкрити наявний purchase flow.

### `IN_TRANSIT`

Відкрити замовлення. Додавання в чергу — лише окрема дозволена дія, якщо чинні правила це підтримують.

### `LENT_TO`

Відкрити позику. Ownership не змінювати автоматично.

## Ідемпотентність

Повторне надсилання тієї самої apply-команди не повинно:

- створювати дублікати;
- повторно зміщувати правильно впорядковані книги;
- пошкоджувати queue positions.

Server має повторно обчислити актуальність fingerprint та повернути стабільний результат або `409 ISSUE_STALE`.
