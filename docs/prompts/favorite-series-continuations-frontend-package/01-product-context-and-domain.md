# 01. Контекст, мета та доменні визначення

> Містить розділи 1–3 початкової специфікації: мету блока, терміни та статуси.

# Блок «Продовжити улюблені серії»

> Повна специфікація логіки, бекенд-завдання, API-контракту, фронтенд-відображення та edge cases.
>
> Документ описує блок правого сайдбара на сторінці **«Улюблені книги»**. Його мета — показати, яку книгу читати далі в серіях, де користувач уже має хоча б одну улюблену книгу.
>
> Перед реалізацією обов’язково провести read-only аудит актуального коду. Не дублювати наявну логіку серій, порядку книг, статусів читання, володіння, черги читання та формування `BookView`.

---

## 1. Мета блока

Блок **«Продовжити улюблені серії»** допомагає користувачу швидко зрозуміти:

- у яких серіях є улюблені книги;
- яка книга є наступною за логікою читання кожної такої серії;
- чи доступна ця книга зараз;
- що з нею можна зробити: продовжити читання, почати читати, додати в чергу, відкрити покупку або додати до списку «Хочу купити».

Блок не є:

- списком усіх улюблених книг;
- списком усіх серій;
- випадковою рекомендацією;
- списком книг, які йдуть безпосередньо після конкретної улюбленої книги;
- дублем швидких чіпів «Читаю», «Прочитано», «Частина серії»;
- блоком статистики.

Ключове правило:

> Для кожної серії потрібно знайти **першу актуальну книгу за канонічним порядком серії**, яка ще потребує дії користувача.

---

## 2. Основні визначення

### 2.1. Улюблена серія в контексті блока

У цій задачі «улюблена серія» — це не окремий прапорець на серії.

Серія вважається релевантною для блока, якщо:

```text
у серії є хоча б одна книга користувача з isFavorite = true
```

Одна серія має потрапляти до результату лише один раз, навіть якщо у ній кілька улюблених книг.

### 2.2. Наступна книга серії

Наступна книга — це не обов’язково книга, яка стоїть після улюбленої.

Наступна книга визначається на основі:

1. канонічного порядку книг у серії;
2. поточного статусу читання кожної книги;
3. правила, які статуси вважаються завершеними для руху далі.

Приклад:

```text
Книга 1 — finished
Книга 2 — not_started
Книга 3 — finished + isFavorite
Книга 4 — not_started
```

Наступною має бути:

```text
Книга 2
```

Не книга 4, хоча вона стоїть після улюбленої книги №3.

### 2.3. Канонічний порядок серії

Потрібно повторно використати той самий порядок, який уже застосовується:

- на сторінці деталей серії;
- у списку книг серії;
- у логіці «наступної книги»;
- у доменній моделі серій.

Не можна визначати порядок через:

- `createdAt`;
- `updatedAt`;
- дату додавання книги користувачем;
- алфавіт;
- випадкове сортування.

Якщо в проєкті є поле на кшталт:

```text
seriesPosition
seriesOrder
bookNumber
volumeNumber
sequence
```

воно має бути джерелом істини.

---

## 3. Поточні статуси, які потрібно врахувати

### 3.1. Статус читання

За поточною моделлю очікуються статуси:

```text
not_started
want_to_read
reading
paused
finished
dnf
```

Перед реалізацією потрібно перевірити їх актуальні enum-значення у shared schemas та Prisma.

### 3.2. Статус володіння

Очікуються:

```text
NONE
WANT_TO_BUY
IN_TRANSIT
OWNED
BORROWED_FROM
LENT_TO
```

Перед реалізацією перевірити фактичні назви й поточну бізнес-логіку.

### 3.3. Статус у черзі читання

Якщо в `BookView` або окремому endpoint уже доступні:

- факт перебування у черзі;
- позиція;
- пріоритет;

їх потрібно повторно використати для CTA на фронтенді.

Не додавати нові queue-поля лише для цього блока, якщо вони вже доступні в поточній моделі книги.
