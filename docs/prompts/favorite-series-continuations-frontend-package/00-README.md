# Пакет реалізації: «Продовжити улюблені серії»

Цей пакет підготовлений для фронтенд-агента. Велика специфікація розділена на коротші логічні документи, щоб агент міг послідовно:

1. провести read-only аудит коду та фактичного бекенд-контракту;
2. порівняти реалізацію бекенду зі специфікацією;
3. зафіксувати розбіжності, не переписуючи бекенд;
4. реалізувати фронтенд-блок у правому сайдбарі сторінки «Улюблені книги»;
5. додати стани, i18n, invalidation та тести;
6. перевірити результат за acceptance criteria.

## Порядок читання

1. `10-CLAUDE-CODE-PROMPT.md` — готовий промпт, який потрібно передати Claude Code разом із цим ZIP.
2. `01-product-context-and-domain.md` — мета, терміни та статуси.
3. `02-backend-audit.md` — що саме знайти у коді до реалізації.
4. `03-backend-selection-and-ranking.md` — очікувана бізнес-логіка бекенду.
5. `04-backend-api-contract.md` — очікуваний endpoint і response shape.
6. `05-backend-technical-requirements.md` — вимоги до актуалізації та ізоляції даних.
7. `06-backend-edge-cases-and-tests.md` — перевірка повноти бекенду.
8. `07-frontend-layout-and-actions.md` — основна фронтенд-реалізація.
9. `08-frontend-states-i18n-a11y.md` — UI-стани, i18n, accessibility.
10. `09-acceptance-scope-and-summary.md` — фінальний checklist.

## Головне правило для агента

Специфікація описує очікувану поведінку, але джерелом істини щодо вже реалізованого API є актуальний код бекенду та shared schemas. Агент не повинен вигадувати поля або дублювати на фронтенді алгоритм `nextBook`.

Коли бекенду бракує для коректної фронтенд-реалізації, агент повинен:

- не реалізовувати бекенд самостійно;
- не підміняти відсутні дані евристикою на фронтенді;
- створити окремий файл `docs/favorite-series-continuations-backend-gaps.md` із конкретним описом нестачі.
