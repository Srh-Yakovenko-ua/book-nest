# 03. Бекенд-логіка вибору та ранжування

> Містить розділи 5–12: кандидатів, closed statuses, nextBook, порядок, доступність і ranking.

## 5. Які серії є кандидатами

Серія є кандидатом, якщо виконуються всі умови:

```text
series належить поточному користувачу або доступна йому за чинною моделлю;
у серії є хоча б одна книга з isFavorite = true;
серія не видалена;
серія не прихована згідно з чинними правилами;
у серії можна визначити канонічний порядок;
у серії є книга, яка потребує наступної дії.
```

### Не включати

- серії без улюблених книг;
- серії, де всі відомі книги завершені;
- серії без жодної книги;
- видалені або недоступні серії;
- серії з повністю невизначеним порядком, якщо неможливо надійно встановити наступну книгу;
- соло-книги без серії.

---

## 6. Які статуси блокують або завершують прогрес

Рекомендована логіка:

### 6.1. Завершені для проходження серії

```text
finished
dnf
```

`finished` означає, що книгу завершено.

`dnf` означає свідоме припинення читання. Така книга не повинна назавжди блокувати перехід до наступної книги серії.

Тому для пошуку наступної книги `dnf` рекомендується вважати **закритим станом**, але не «прочитаною» книгою для статистики.

### 6.2. Незавершені й актуальні

```text
reading
paused
want_to_read
not_started
```

Перша книга в канонічному порядку з одним із цих статусів стає кандидатом.

### 6.3. Якщо поточна продуктова логіка інша

Якщо проєкт уже трактує `dnf` як незавершену книгу, потрібно:

- не змінювати правило локально лише для цього блока;
- використати чинну доменну семантику;
- зафіксувати це у документації.

---

## 7. Алгоритм визначення наступної книги

Для кожної серії-кандидата:

1. Отримати всі відомі книги серії, доступні поточному користувачу.
2. Відсортувати їх канонічно.
3. Нормалізувати статус читання через чинну доменну логіку.
4. Ігнорувати книги зі станом, який вважається закритим для проходження.
5. Знайти першу книгу, що залишається актуальною.
6. Повернути її як `nextBook`.
7. Якщо такої книги немає — серію не показувати.

Псевдокод:

```ts
const CLOSED_STATUSES = new Set(["finished", "dnf"]);

function resolveNextSeriesBook(orderedBooks) {
  return orderedBooks.find((book) => !CLOSED_STATUSES.has(book.readingStatus)) ?? null;
}
```

Використати доменні enum та helper-функції, а не рядки напряму.

## 8. Важливі приклади

### 8.1. Улюблена книга пізніше за пропущену

```text
1 — finished
2 — not_started
3 — finished + favorite
4 — not_started
```

Результат:

```text
nextBook = 2
```

### 8.2. Кілька улюблених книг в одній серії

```text
1 — finished + favorite
2 — finished + favorite
3 — not_started
```

Результат:

```text
один елемент серії;
nextBook = 3;
favoriteBooksCount = 2.
```

### 8.3. Серію ще не починали

```text
1 — not_started
2 — favorite + not_started
3 — not_started
```

Результат:

```text
nextBook = 1
```

### 8.4. Книгу вже читають

```text
1 — finished
2 — reading
3 — favorite + finished
```

Результат:

```text
nextBook = 2
candidateState = active_reading
```

### 8.5. Книгу призупинено

```text
1 — finished
2 — paused
3 — favorite + finished
```

Результат:

```text
nextBook = 2
candidateState = paused
```

### 8.6. Попередню книгу позначено DNF

```text
1 — finished
2 — dnf
3 — not_started
4 — favorite + finished
```

За рекомендованим правилом:

```text
nextBook = 3
```

### 8.7. Усі книги завершено

```text
1 — finished + favorite
2 — finished
3 — dnf
```

Результат:

```text
серію не показувати
```

### 8.8. Серія продовжується, але наступної відомої книги немає

```text
seriesStatus = ongoing
усі наявні книги = finished
майбутня книга ще не створена в системі
```

Результат:

```text
серію не показувати у цьому action-блоці
```

Не створювати фейковий запис «Очікується наступна книга».

## 9. Порядок книг і складні випадки

### 9.1. Пропущені позиції

```text
1, 2, 4, 5
```

Якщо це чинний валідний порядок, сортувати за позицією:

```text
1 → 2 → 4 → 5
```

Не створювати відсутню книгу №3.

### 9.2. Дробові позиції та новели

```text
1
1.5
2
```

Використати точний тип поля й поточну доменну логіку.

Не приводити позицію до integer.

### 9.3. Нульові або від’ємні позиції

Якщо проєкт підтримує пріквели:

```text
0
-1
```

вони мають сортуватися згідно з чинним канонічним алгоритмом.

### 9.4. `null` у позиції

Рекомендована поведінка:

1. Спочатку використати наявний fallback із series details.
2. Якщо fallback немає:
   - книги з визначеною позицією сортувати першими;
   - книги без позиції не використовувати як «наступні», якщо це може дати хибний результат.
3. Якщо вся серія без позицій і немає іншого канонічного порядку — виключити серію з блока.

Не використовувати `createdAt` як прихований канонічний порядок.

### 9.5. Дублікати позицій

Якщо дві книги мають однакову позицію:

- застосувати чинний стабільний tiebreaker;
- за відсутності — `publishedAt`, потім `id`;
- зафіксувати data-quality проблему;
- не робити запит недетермінованим.

### 9.6. Спін-офи та паралельні гілки

Якщо модель серії має окремі підсерії або reading paths, потрібно використовувати наявну структуру.

Якщо модель — лише плоский список, не намагатися самостійно вгадати альтернативний порядок.

## 10. Визначення доступності наступної книги

Після знаходження `nextBook` потрібно визначити, наскільки швидко користувач може перейти до читання.

### 10.1. Доступна зараз

```text
OWNED
BORROWED_FROM
```

### 10.2. Тимчасово недоступна

```text
LENT_TO
IN_TRANSIT
```

### 10.3. Ще не придбана

```text
WANT_TO_BUY
NONE
```

Ці групи потрібні для сортування серій та вибору CTA, але бекенд не повинен повертати локалізовані тексти.

## 11. Пріоритет серій у правому барі

Блок показує до трьох серій. Якщо кандидатів більше, їх потрібно ранжувати детерміновано.

Рекомендований порядок:

### Пріоритет 1 — активне читання

```text
nextBook.readingStatus = reading
```

### Пріоритет 2 — призупинене читання

```text
nextBook.readingStatus = paused
```

### Пріоритет 3 — можна почати зараз

```text
ownership IN (OWNED, BORROWED_FROM)
readingStatus IN (not_started, want_to_read)
```

### Пріоритет 4 — книга вже належить користувачу, але позичена комусь

```text
ownership = LENT_TO
```

### Пріоритет 5 — книга в дорозі

```text
ownership = IN_TRANSIT
```

### Пріоритет 6 — книга у списку покупок

```text
ownership = WANT_TO_BUY
```

### Пріоритет 7 — книги немає у власній бібліотеці

```text
ownership = NONE
```

### Tiebreakers

У межах одного пріоритету:

1. остання активність у серії, якщо є надійне поле;
2. найновіший `favoriteAddedAt` серед улюблених книг серії;
3. стабільний `seriesId`.

Якщо окремого поля активності серії немає, не створювати його в межах MVP лише заради цього блока. Використати:

```text
MAX(favoriteAddedAt)
```

як основний recency tiebreaker.

---

## 12. Серії з однаковою наступною книгою

За коректної моделі одна книга не повинна належати до двох серій в одному й тому самому sequence-зв’язку.

Якщо книга може входити до кількох серій:

- результат має бути один на серію;
- одна книга технічно може повторитися в різних series items;
- фронтенд не повинен самостійно дедуплікувати серії;
- потрібно дотримуватися чинної моделі зв’язків.
