# 05. Технічні вимоги до бекенду

> Містить розділи 16–19: продуктивність, індекси, актуалізацію та ізоляцію даних.

## 16. Продуктивність і запити до БД

Не можна реалізовувати N+1:

```text
1 запит на серії
+ окремий запит на книги кожної серії
+ окремий запит на прогрес кожної книги
```

Потрібно:

- використати агрегований query;
- завантажити релевантні серії та їхні книги пакетно;
- виконати обчислення в repository/service без десятків окремих звернень;
- обмежити вибірку полями, потрібними контракту.

Якщо Prisma не дозволяє елегантно обчислити «першу незакриту книгу» одним query, допустимо:

1. одним запитом отримати всі релевантні серії;
2. одним або кількома пакетними запитами отримати книги цих серій;
3. обчислити наступні книги в пам’яті;
4. відсортувати;
5. застосувати limit.

Але не виконувати запит окремо для кожної серії.

## 17. Індекси

Перед додаванням індексів перевірити поточну Prisma schema та обсяг таблиць.

Потенційно корисні поля:

```text
Book.userId
Book.isFavorite
Book.seriesId
SeriesBook.seriesId
SeriesBook.position
BookReadingProgress.bookId
```

Не додавати індекс автоматично без аналізу існуючих індексів і фактичного SQL.

---

## 18. Кешування та актуалізація

Блок має оновлюватися після:

- додавання або видалення книги з улюблених;
- зміни статусу читання;
- зміни ownership;
- додавання книги до серії;
- зміни порядку книг;
- видалення книги із серії;
- зміни черги читання, якщо queue показується;
- завершення книги;
- позначення DNF.

Якщо використовується React Query:

- endpoint має мати окремий query key;
- frontend mutation має інвалідовувати цей query;
- не покладатися на довгий stale cache без invalidation.

---

## 19. Авторизація та ізоляція даних

Усі обчислення виконуються лише для поточного користувача.

Обов’язкове обмеження:

```text
book.userId = currentUserId
```

Не приймати `userId` з query.

Не враховувати:

- чужі улюблені книги;
- чужі статуси читання;
- чужий ownership;
- чужу чергу.
