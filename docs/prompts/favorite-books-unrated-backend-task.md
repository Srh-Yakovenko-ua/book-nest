# Улюблені книги без оцінки — аналіз поточної підтримки та завдання для бекенду

> Документ описує логіку блока **«Улюблені без оцінки»** на сторінці «Улюблені книги», наявні можливості бекенду, прогалини та завдання для бекенд-агента.
>
> Перед внесенням змін потрібно перевірити актуальний стан гілки та повторно використати наявні модулі, DTO, репозиторії, фільтри, пагінацію й механізм роботи з рейтингом.

---

## 1. Мета функціоналу

На сторінці **«Улюблені книги»** потрібно додати правий інформаційний блок:

## «Улюблені без оцінки»

Блок має допомагати знайти улюблені книги, для яких користувач ще не встановив рейтинг, і швидко перейти до оцінювання.

Блок не повинен:

- дублювати верхні статистичні картки;
- дублювати наявні чіпи швидких фільтрів;
- створювати окрему сутність `favorites`;
- завантажувати всі улюблені книги на фронтенд лише для локального пошуку книг без оцінки;
- рахувати книги лише в межах поточної сторінки пагінації.

Бекенд має повертати точну кількість таких книг і невеликий список для прев’ю.

---

## 2. Запланований вигляд та поведінка блока

Приклад:

```text
Улюблені без оцінки                         3

Книги, яким ще не поставлено оцінку

[обкладинка] Назва книги
             Автор
             [Оцінити]

[обкладинка] Назва книги
             Автор
             [Оцінити]

[обкладинка] Назва книги
             Автор
             [Оцінити]

Переглянути всі →
```

### Дані для кожної книги

Для прев’ю достатньо повернути ті самі поля, які вже використовуються у звичайній картці або компактному представленні книги:

- `id`;
- `title`;
- автор або список авторів;
- обкладинка;
- статус читання;
- поточний рейтинг або `null`;
- `favoriteAddedAt`;
- інші обов’язкові поля поточного `BookView`, якщо список книг уже повертається через спільний view model.

Не потрібно створювати окремий спеціальний view model, якщо чинний `BookView` підходить для цього блока без зайвих важких даних.

### Дії

- Натискання на книгу відкриває сторінку деталей книги.
- Натискання на **«Оцінити»** використовує наявний механізм встановлення рейтингу.
- Після успішного оцінювання:
  - книга більше не відповідає фільтру `без оцінки`;
  - кількість книг без оцінки зменшується;
  - список прев’ю оновлюється;
  - середній рейтинг улюблених перераховується.

### Посилання «Переглянути всі»

Має застосувати до основного списку фільтр:

- тільки улюблені;
- тільки без оцінки;
- за потреби — тільки прочитані, якщо така бізнес-логіка буде затверджена.

---

## 3. Поточна підтримка улюблених книг на бекенді

Окремої сутності або таблиці `favorites` немає.

Улюбленість зберігається безпосередньо на моделі `Book`:

```prisma
isFavorite      Boolean   @default(false) @map("is_favorite")
favoriteAddedAt DateTime? @map("favorite_added_at") @db.Timestamptz
```

### Уже доступні можливості

#### Одиночне додавання або видалення з улюблених

```http
PATCH /api/books/:id
```

У body передається:

```json
{
  "isFavorite": true
}
```

або:

```json
{
  "isFavorite": false
}
```

#### Масова зміна

```http
PATCH /api/books/bulk/favorite
```

```json
{
  "bookIds": ["uuid-1", "uuid-2"],
  "isFavorite": true
}
```

#### Отримання списку улюблених

```http
GET /api/books?isFavorite=true
```

#### Сортування за датою додавання в улюблені

Підтримуються:

```text
favorite_added_desc
favorite_added_asc
```

#### Агрегована статистика

```http
GET /api/books/favorites-summary
```

Поточна відповідь:

```ts
{
  (total, reading, finished, wantToRead, series, solo, averageRating);
}
```

### Уже наявні дані, корисні для нового блока

- `isFavorite`;
- `favoriteAddedAt`;
- список улюблених книг;
- сортування за датою додавання в улюблені;
- `averageRating`;
- рейтинг книги у `BookReadingProgress`;
- загальна логіка перевірки власності через `userId`;
- загальні механізми пагінації, фільтрації та сортування книг.

---

## 4. Чого зараз не вистачає

За наданим аналізом бекенду немає підтвердженої підтримки:

1. Фільтра списку книг за наявністю або відсутністю рейтингу.
2. Точної кількості улюблених книг без оцінки.
3. Окремого поля `unrated` у `favorites-summary`.
4. Готового запиту, який повертає перші 3 улюблені книги без оцінки.
5. Чітко зафіксованої бізнес-логіки:
   - чи рахувати всі улюблені книги без оцінки;
   - чи рахувати лише прочитані улюблені книги без оцінки;
   - чи дозволено ставити рейтинг книзі, яка ще не має статусу `finished`.

Тому перед реалізацією потрібно перевірити актуальний код.

---

## 5. Обов’язковий аудит перед змінами

Бекенд-агент має спочатку виконати read-only аналіз і зафіксувати, що вже реалізовано.

### Перевірити модель рейтингу

Знайти:

- де саме зберігається `rating`;
- чи є рейтинг полем `BookReadingProgress`;
- чи існує окремий запис прогресу для кожної книги;
- чи може запис прогресу бути відсутнім;
- чи може запис існувати з `rating = null`;
- який діапазон рейтингу;
- чи дозволені дробові значення;
- чи є одна оцінка на книгу для одного користувача;
- як рейтинг створюється, оновлюється та видаляється.

### Перевірити API рейтингу

Знайти наявний endpoint або mutation для встановлення рейтингу.

Потрібно визначити:

- маршрут;
- DTO;
- валідацію;
- перевірку власності;
- поведінку при повторному встановленні;
- чи можна очистити рейтинг;
- чи оновлюється `updatedAt`;
- чи є тести.

Якщо API рейтингу вже існує, новий endpoint для кнопки **«Оцінити»** створювати не потрібно.

Якщо API рейтингу немає, його потрібно реалізувати у відповідному модулі прогресу читання, а не всередині логіки улюблених книг.

### Перевірити поточні фільтри `GET /api/books`

Перевірити:

- `LibraryBooksQuerySchema`;
- input DTO;
- service;
- repository;
- Prisma `where`;
- пагінацію;
- сортування;
- підтримувані статуси читання;
- фільтрацію за рейтингом;
- фільтрацію за `rating === null`;
- можливість комбінувати кілька фільтрів.

Особливо перевірити, чи вже існує один із параметрів:

```text
hasRating
isRated
rating
ratingFrom
ratingTo
ratingStatus
```

Якщо еквівалентний фільтр уже є, потрібно повторно використати його, а не створювати дубль.

### Перевірити `favorites-summary`

Знайти:

- `FavoritesSummaryViewSchema`;
- view DTO;
- repository aggregation;
- service;
- controller;
- тести.

Перевірити, чи поле з кількістю книг без оцінки вже не було додано в актуальній гілці.

## 6. Рекомендована бізнес-логіка

### Базове визначення

Улюблена книга без оцінки — це книга, яка:

```text
book.userId = currentUserId
book.isFavorite = true
rating is null or rating record does not exist
```

### Важливе рішення щодо статусу читання

Для блока з кнопкою **«Оцінити»** рекомендовано вважати корисними насамперед книги зі статусом:

```text
finished
```

Тому перед реалізацією потрібно перевірити продуктову логіку.

#### Рекомендований варіант для MVP

Поле `unrated` у статистиці та список блока рахують:

```text
isFavorite = true
readingStatus = finished
rating is null
```

Переваги:

- блок показує лише книги, які логічно вже можна оцінити;
- користувача не підштовхують оцінювати непрочитані книги;
- CTA **«Оцінити»** завжди доречний;
- порожній стан має однозначний сенс.

У такому разі текст блока означає:

> Прочитані улюблені книги, яким ще не поставлено оцінку.

#### Альтернативний варіант

Рахувати всі улюблені книги без оцінки незалежно від статусу читання.

Цей варіант можна використовувати лише якщо в продукті дозволено й очікується оцінювання непрочитаних книг.

### Необхідно зафіксувати рішення

Перед написанням коду бекенд-агент має явно зазначити в результаті аналізу:

```text
Обраний критерій unrated:
A. лише finished;
або
B. усі статуси.
```

Якщо в чинному коді вже є загальна бізнес-логіка рейтингу, потрібно дотримуватися її.

---

## 7. Рекомендовані зміни API

Не потрібно створювати окремий модуль або endpoint на кшталт:

```text
GET /api/favorites/unrated
```

Функціонал варто вбудувати в наявний модуль `books`.

---

## 7.1. Додати загальний фільтр за наявністю рейтингу

Рекомендований параметр:

```ts
hasRating?: boolean
```

Для query string використати той самий підхід, який уже застосовується для `isFavorite`, наприклад `z.stringbool()`.

Приклад:

```http
GET /api/books?isFavorite=true&hasRating=false
```

Якщо для блока обрано лише прочитані книги:

```http
GET /api/books?isFavorite=true&hasRating=false&readingStatus=finished
```

Для прев’ю:

```http
GET /api/books?isFavorite=true&hasRating=false&readingStatus=finished&limit=3
```

Назви параметрів пагінації потрібно взяти з чинного API. Не створювати нові `limit`, `page`, `cursor`, якщо в проєкті вже використовується інша схема.

### Семантика `hasRating`

```text
hasRating=true
```

Книга має ненульовий рейтинг.

```text
hasRating=false
```

- запис прогресу відсутній; або
- запис прогресу існує, але `rating = null`.

### Комбінація фільтрів

Фільтр має коректно комбінуватися з:

- `isFavorite`;
- статусом читання;
- пошуком;
- авторами;
- серіями;
- іншими наявними фільтрами;
- пагінацією;
- сортуванням.

---

## 7.2. Розширити `favorites-summary`

Додати поле:

```ts
unrated: number;
```

Оновлена відповідь:

```ts
{
  (total, reading, finished, wantToRead, series, solo, averageRating, unrated);
}
```

`unrated` має використовувати той самий критерій, що й список блока.

Не можна рахувати `unrated` на фронтенді як:

```text
total - кількість книг із рейтингом на поточній сторінці
```

Це буде некоректно через пагінацію, фільтри та можливу відсутність завантажених книг.

### Узгодженість агрегатів

Після встановлення або видалення рейтингу:

- `unrated` має змінитися;
- `averageRating` має бути перерахований;
- `total` не змінюється;
- книга залишається улюбленою, якщо `isFavorite` не змінювався.

---

## 8. Рекомендоване сортування прев’ю

Для блока потрібно повернути не більше трьох книг.

Рекомендований порядок:

1. Найновіші за `favoriteAddedAt`.
2. Далі чинні стабільні tiebreakers проєкту:
   - `createdAt`;
   - `id`;
   - або інші вже наявні правила.

Якщо використовується поточне сортування:

```text
favorite_added_desc
```

потрібно повторно використати його.

Не створювати окреме спеціальне сортування лише для правого бара без необхідності.

---

## 9. Порожні стани

### Немає улюблених книг

```text
Улюблених книг поки немає
```

### Улюблені є, але всі вже оцінено

```text
Усі улюблені вже оцінено
```

### Якщо враховуються лише прочитані книги

```text
Серед прочитаних улюблених немає книг без оцінки
```

### Є непрочитані без оцінки, але блок працює лише з `finished`

Вони не повинні входити до `unrated`.

Це потрібно зафіксувати в API-документації, щоб фронтенд і бекенд однаково розуміли значення поля.

---

## 10. Обробка зміни станів

### Користувач ставить оцінку

Було:

```text
isFavorite = true
rating = null
```

Стало:

```text
isFavorite = true
rating = 9
```

Очікування:

- книга зникає зі списку `hasRating=false`;
- `unrated` зменшується на 1;
- `averageRating` перераховується.

### Користувач видаляє оцінку

Було:

```text
isFavorite = true
rating = 9
```

Стало:

```text
isFavorite = true
rating = null
```

Очікування:

- книга з’являється у списку `hasRating=false`;
- `unrated` збільшується на 1;
- `averageRating` перераховується.

### Користувач прибирає книгу з улюблених

Було:

```text
isFavorite = true
rating = null
```

Стало:

```text
isFavorite = false
rating = null
```

Очікування:

- книга зникає з блока;
- `unrated` зменшується;
- `total` зменшується;
- інші агрегати улюблених перераховуються.

### Змінюється статус читання

Якщо `unrated` рахує лише `finished`:

- перехід у `finished` без рейтингу додає книгу до блока;
- вихід із `finished` прибирає книгу з блока;
- встановлення рейтингу прибирає книгу з блока незалежно від дати додавання в улюблені.

---

## 11. Перевірка власності та безпеки

Усі запити мають працювати лише в межах поточного користувача.

Обов’язкові умови:

```text
book.userId = currentUserId
```

Не можна:

- повертати чужі книги;
- рахувати чужі рейтинги;
- дозволяти встановлювати рейтинг чужій книзі;
- приймати `userId` із query або body як джерело істини.

Потрібно використовувати поточний `JwtAccessGuard` та наявний підхід `findOwnedById`.

---

## 12. Продуктивність

Потрібно перевірити, як побудований зв’язок між `Book` і `BookReadingProgress`.

Запит для `hasRating=false` має коректно обробляти:

- відсутність relation row;
- relation row із `rating = null`.

Не потрібно спочатку завантажувати всі книги в пам’ять і фільтрувати їх у service.

Фільтрація та count мають виконуватися на рівні БД.

### Індекси

Перед додаванням нового індексу перевірити:

- обсяг таблиці;
- наявні індекси;
- фактичний Prisma query;
- чи є індекс за `userId`;
- чи потрібен складений індекс, наприклад за `userId` та `isFavorite`.

Не додавати індекс автоматично без аналізу плану та наявної схеми.

---

## 13. DTO та shared schemas

Потрібно оновити спільні схеми в `packages/shared/src/books.ts` або їх актуальному місці.

### Query schema

Якщо еквівалентного фільтра ще немає:

```ts
hasRating: z.stringbool().optional();
```

Назву потрібно узгодити з поточним стилем API.

### Favorites summary schema

Додати:

```ts
unrated: z.number().int().nonnegative();
```

### View DTO

Оновити `FavoritesSummaryViewSchema` та відповідний `createZodDto`.

Не дублювати типи вручну, якщо вони виводяться зі схем.

---

## 14. Тести

Потрібно додати або оновити тести на всіх релевантних рівнях проєкту.

### Фільтр `hasRating=false`

Перевірити:

1. Улюблена книга без progress row повертається.
2. Улюблена книга з `rating = null` повертається.
3. Улюблена книга з рейтингом не повертається.
4. Неулюблена книга без рейтингу не повертається при `isFavorite=true`.
5. Чужа книга не повертається.
6. Фільтр працює разом зі статусом `finished`.
7. Пагінація повертає коректні `total` і items.
8. Сортування стабільне.
9. `hasRating=true` повертає лише книги з рейтингом.

### `favorites-summary.unrated`

Перевірити:

1. Немає улюблених книг → `unrated = 0`.
2. Є одна улюблена без progress row → `unrated = 1`.
3. Є одна улюблена з `rating = null` → `unrated = 1`.
4. Після встановлення рейтингу → `unrated = 0`.
5. Після очищення рейтингу → `unrated = 1`.
6. Неулюблені книги не враховуються.
7. Чужі книги не враховуються.
8. Якщо правило лише для `finished`, інші статуси не враховуються.
9. `averageRating` не включає `null`.
10. Повторний запит не змінює дані.

### API-валідація

Перевірити:

- `hasRating=true`;
- `hasRating=false`;
- неправильні значення;
- відсутність параметра;
- комбінацію з іншими query-параметрами.

## 16. Acceptance Criteria

Функціонал готовий, коли:

- [ ] Перевірено й задокументовано поточний механізм рейтингу.
- [ ] Перевірено, чи вже існує фільтр книг за відсутністю рейтингу.
- [ ] `GET /api/books` підтримує отримання улюблених книг без оцінки або повторно використовує вже наявний еквівалентний фільтр.
- [ ] Фільтр працює на рівні БД, а не лише для завантаженої сторінки.
- [ ] `GET /api/books/favorites-summary` повертає `unrated`.
- [ ] `unrated` і список використовують однакову бізнес-умову.
- [ ] Враховується відсутній progress row та `rating = null`.
- [ ] Дані ізольовані за `userId`.
- [ ] Для прев’ю можна запросити не більше трьох книг через наявну пагінацію.
- [ ] Підтримується чинне сортування `favorite_added_desc`.
- [ ] Після встановлення рейтингу книга більше не потрапляє до `hasRating=false`.
- [ ] Після видалення рейтингу книга знову потрапляє до `hasRating=false`.
- [ ] Оновлено shared schemas і DTO.
- [ ] Додано тести для позитивних, негативних і граничних випадків.
- [ ] Старі endpoints улюблених книг не зламані.
- [ ] Не створено зайву сутність або таблицю `favorites`.

## 17. Що не потрібно реалізовувати

У межах цієї задачі не потрібно:

- створювати історію оцінок;
- створювати історію додавання та видалення з улюблених;
- створювати окрему таблицю favorites;
- створювати рекомендаційну систему;
- випадково вибирати книгу;
- додавати новий спеціалізований endpoint, якщо задачу закриває `GET /api/books`;
- змінювати логіку `favoriteAddedAt`;
- змінювати bulk favorite;
- повертати кількість оцінених книг, якщо вона не потрібна іншим екранам;
- реалізовувати UI правого бара на бекенді.

## 18. Рекомендований контракт для фронтенду

### Статистика

```http
GET /api/books/favorites-summary
```

```json
{
  "total": 9,
  "reading": 0,
  "finished": 9,
  "wantToRead": 0,
  "series": 6,
  "solo": 3,
  "averageRating": 8.9,
  "unrated": 3
}
```

### Прев’ю книг без оцінки

При рекомендованій логіці лише для прочитаних:

```http
GET /api/books?isFavorite=true&hasRating=false&readingStatus=finished&sort=favorite_added_desc
```

До запиту потрібно додати чинний параметр обмеження кількості елементів, щоб повернути 3 книги.

### Перегляд усіх

Той самий фільтр без обмеження правого бара, із чинною пагінацією списку.

## 19. Підсумок

Поточний бекенд уже має основну інфраструктуру:

- улюбленість на `Book`;
- `favoriteAddedAt`;
- список улюблених;
- сортування;
- статистику;
- середній рейтинг;
- per-user ізоляцію.

Для блока **«Улюблені без оцінки»** найімовірніше потрібно:

1. Перевірити наявний API рейтингу.
2. Додати або повторно використати фільтр книг за відсутністю рейтингу.
3. Додати `unrated` у `favorites-summary`.
4. Використати чинну пагінацію для прев’ю з трьох книг.
5. Зафіксувати, чи враховуються лише прочитані книги.
6. Покрити логіку тестами.

Ключовий принцип: не створювати окрему favorites-архітектуру, а розширити вже наявний універсальний список книг і поточну агрегацію улюблених.
