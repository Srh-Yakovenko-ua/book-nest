# Бекенд-завдання: лічильники книг для швидких фільтрів бібліотеки

## Навіщо (контекст)

На сторінках **«Усі книги»**, **«Моя бібліотека»** та **«Улюблені»** є рядок швидких фільтрів — чипи:
Усі, Читаю, Хочу прочитати, Прочитано, Улюблені, До покупки, В дорозі, Позичені, Серії, Соло.

Продукт хоче, щоб поруч із назвою кожного чипа показувалася **кількість книг, що підпадають під цей фільтр** (напр. «Улюблені 9», «Серії 14»). Фронт уже вміє це відрендерити — бракує лише даних із бекенду. Тому це завдання **суто про дані**: ендпоінти мають повернути потрібні лічильники.

## Мета

Ендпоінти, що живлять ці три сторінки, повинні повертати кількість книг для **кожного** швидкого фільтра, порахованих у межах базового scope відповідної сторінки.

## Поточний стан (що вже віддається)

- `GET /api/books/overview` (живить «Усі книги» та «Моя бібліотека») повертає summary з полями: `total`, `reading` (reading + rereading), `finished`, `favorites`.
- Ендпоінт favorites-summary (живить «Улюблені») повертає: `total`, `reading`, `finished`, `averageRating`.

Тобто лічильники **вже є** для чипів: **Усі**, **Читаю**, **Прочитано**, **Улюблені**. Для решти — немає.

## Чого бракує

Немає лічильників для цих фільтрів:

| Чип (фронтовий ключ)            | Предикат «книга підпадає під фільтр, якщо…»                  | На яких сторінках показується  |
| ------------------------------- | ------------------------------------------------------------ | ------------------------------ |
| `want_to_read` (Хочу прочитати) | `readingStatus = want_to_read`                               | усі 3                          |
| `want_to_buy` (До покупки)      | `ownershipStatus = want_to_buy`                              | лише «Усі книги»               |
| `in_transit` (В дорозі)         | `ownershipStatus = in_transit`                               | лише «Усі книги»               |
| `borrowed` (Позичені)           | `ownershipStatus ∈ (borrowed_from_someone, lent_to_someone)` | «Усі книги» + «Моя бібліотека» |
| `series` (Серії)                | `bookType = series_part`                                     | усі 3                          |
| `solo` (Соло)                   | `bookType = solo`                                            | усі 3                          |

## Головна вимога (інваріант)

> Лічильник будь-якого чипа = той самий `totalCount`, який повернув би list-ендпоінт бібліотеки, якби цей швидкий фільтр застосували на цій сторінці.

Тобто для кожного чипа:

```
count = кількість книг, що відповідають (базовий scope сторінки) AND (предикат фільтра)
```

Цей інваріант гарантує, що число на чипі точно збігається з тим, що юзер побачить у списку, натиснувши чип. Будь ласка, дотримуйся саме його — це прибирає крайові випадки взаємодії scope і предиката.

## Базовий scope кожної сторінки

- **«Усі книги»** — усі книги користувача (overview без `owner`).
- **«Моя бібліотека»** — `owner ∈ (owned, lent_to_someone, borrowed_from_someone)` (overview уже отримує цей `owner` у query).
- **«Улюблені»** — `isFavorite = true`.

Приклади взаємодії scope і фільтра (щоб не було сюрпризів):

- На «Моя бібліотека» чип `borrowed` рахується **в межах** owned/lent/borrowed → фактично `borrowed_from_someone + lent_to_someone` серед «моїх». Чипи `want_to_buy` / `in_transit` на цій сторінці не показуються.
- На «Улюблені» чипи `series` / `solo` / `want_to_read` рахуються **лише серед улюблених**.

## Де віддавати дані

Додати в обидва ендпоінти новий об'єкт-лічильник (пропоную назву `quickFilterCounts`):

- у відповідь `GET /api/books/overview` — рахувати в межах `owner`-scope, що вже приходить у query (покриє «Усі книги» + «Моя бібліотека»);
- у відповідь favorites-summary — рахувати в межах `isFavorite = true` (покриє «Улюблені»).

Склад об'єкта `quickFilterCounts` (усі поля — цілі числа ≥ 0):

| Поле         | Що рахує (у межах базового scope сторінки)                   |
| ------------ | ------------------------------------------------------------ |
| `all`        | усі книги в scope                                            |
| `reading`    | `readingStatus ∈ (reading, rereading)`                       |
| `wantToRead` | `readingStatus = want_to_read`                               |
| `finished`   | `readingStatus = finished`                                   |
| `favorites`  | `isFavorite = true`                                          |
| `wantToBuy`  | `ownershipStatus = want_to_buy`                              |
| `inTransit`  | `ownershipStatus = in_transit`                               |
| `borrowed`   | `ownershipStatus ∈ (borrowed_from_someone, lent_to_someone)` |
| `series`     | `bookType = series_part`                                     |
| `solo`       | `bookType = solo`                                            |

Для однорідності віддавай **усі** поля в обох ендпоінтах; на сторінках, де відповідний чип не показується, зайве поле фронт просто ігнорує. (За бажанням можна не рахувати завідомо непотрібні для конкретного scope, але однорідний набір простіший і менш баговий — на твій розсуд.)

## Обмеження / як робити (за архітектурою проєкту)

- Дотримуйся шаруватої архітектури:
  - **контракт** (Zod DTO + типи) — у `packages/shared` (єдине джерело правди для FE/BE);
  - **репозиторій** (`books.repository.ts`) — єдиний шар, що торкається Prisma; це просто додаткові `book.count({ where })` з відповідним `where`; уже є готові хелпери `buildLibraryWhere` / `countForLibrary` — використай їх, щоб `where` збігався з list-ендпоінтом (це і забезпечить інваріант вище);
  - **сервіс** (`books.service.ts`, методи `overview` / `favoritesSummary`) — рахує лічильники та мапить у ViewModel;
  - **контролер** — без логіки.
- Це **read-only агрегації** — **міграції не потрібні**, схему БД не чіпати.
- Один запит на сторінку (не N окремих запитів з фронту). Рахувати паралельно через `Promise.all`, як уже зроблено для наявних лічильників в `overview`.

## Definition of done

- `GET /api/books/overview` і favorites-summary повертають `quickFilterCounts` з усіма полами вище.
- Значення збігаються з `totalCount` відповідного list-запиту (перевірити хоча б на кількох фільтрах).
- Оновлені/додані тести: `books.controller.overview.test.ts`, `books.controller.favorites-summary.test.ts` — покрити коректність лічильників і для непорожніх наборів, і для 0; окремо перевірити взаємодію scope (напр. `borrowed` у «Моя бібліотека», `series` серед «Улюблені»).
- Усі гейти зелені: `pnpm typecheck`, `pnpm lint`, `pnpm test`.

## Приклад перевірки (curl)

Для кожного фільтра значення в `quickFilterCounts` має дорівнювати `totalCount` list-запиту з тим самим фільтром і scope. Наприклад:

- `quickFilterCounts.series` з `GET /api/books/overview` == `totalCount` з `GET /api/books?bookType=series_part`;
- `quickFilterCounts.wantToRead` == `totalCount` з `GET /api/books?status=want_to_read`;
- `quickFilterCounts.borrowed` у scope «Моя бібліотека» == `totalCount` з list-запиту тієї ж сторінки з фільтром «Позичені».

## Поза межами цього завдання

- Рендер чисел на чипах — **фронтова частина**, робиться окремо після того, як ендпоінти почнуть віддавати `quickFilterCounts`. Бекендеру верстку/переклади чіпати не треба.
