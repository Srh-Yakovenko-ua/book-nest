# Відкриті знахідки після ревʼю дедуплікації видавництв

Знайдено під час перевірки гілки `feat/publisher-dedup-matching` на UI. Жодна з цих проблем не стосується самої дедуплікації видавництв, тому в той PR вони не ввійшли. Кожна потребує окремого рішення.

---

## 1. Підпис поля авторів не фокусує поле

**Файл:** `apps/web/src/features/books/components/authors-field.tsx`

`AuthorsField` приймає проп `id` і передає його в `CommandPrimitive.Input`. cmdk рендерить свій інпут так, що власні атрибути йдуть після спреду чужих пропсів:

```js
t.createElement(D.input, {
  ref: o, ...u, "cmdk-input": "", autoComplete: "off", ...,
  "aria-expanded": !0, "aria-labelledby": b.labelId, id: b.inputId, ...
})
```

Наші пропси це `...u`, тож у DOM перемагає cmdk. Мовчки затираються три:

| проп            | що передаємо     | що в DOM                                |
| --------------- | ---------------- | --------------------------------------- |
| `id`            | `"book-author"`  | згенерований `useId`                    |
| `aria-expanded` | `open && !atMax` | завжди `true`                           |
| `autoComplete`  | `"off"`          | `"off"` (те саме, просто мертвий рядок) |

Наслідки:

1. `<Label htmlFor="book-author">` вказує на елемент, якого в DOM немає. Клік по підпису не фокусує поле. На тачі це часто основний спосіб влучити в поле.
2. `role="combobox"` завжди рапортує `aria-expanded="true"`, навіть коли попап закритий. Це обмеження cmdk, згори його не перебити. Але наш рядок `aria-expanded={open && !atMax}` створює враження, що стан керований, і наступний читач буде в цьому впевнений.

Доступна назва поля при цьому ціла: корінь cmdk рендерить прихований `<label cmdk-label htmlFor={inputId} id={labelId}>`, куди йде текст із `<CommandPrimitive label={...}>`, і `aria-labelledby` вказує саме туди. Скрінрідер називає поле правильно. Ламається лише клік.

### Чому не можна скопіювати рішення від видавництва

Для поля видавництва це полагоджено глобальним `document.querySelector('[data-slot="..."]')`. Тут такий підхід дасть баг: на сторінці створення книги живуть два екземпляри `AuthorsField` одночасно. Перший у самій формі (`book-form.tsx:853`), другий усередині діалогу нової серії (`book-type-section.tsx:233` → `create-series-dialog.tsx:168`). Глобальний селектор знайде перший збіг у документі, тож клік по підпису в діалозі перекине фокус у форму за спиною діалогу.

### Пропозиція

Замінити `id` на ref. Ref cmdk не затирає, бо `forwardRef` дістає його окремим аргументом до спреду.

1. У `authors-field.tsx` прибрати з `CommandPrimitive.Input` пропси `id`, `aria-expanded` і `autoComplete`, додати `ref={inputRef}`. Тип пропсів:

   ```ts
   type AuthorsFieldProps = {
     describedBy?: string;
     inputRef: RefObject<Nullable<HTMLInputElement>>;
     invalid: boolean;
     onChange: (next: AuthorSelection[]) => void;
     value: AuthorSelection[];
   };
   ```

2. Там же експортувати хук, який володіє ref'ом:

   ```ts
   export function useAuthorsFieldFocus() {
     const inputRef = useRef<Nullable<HTMLInputElement>>(null);
     return {
       fieldProps: { inputRef },
       labelProps: { className: "cursor-pointer", onClick: () => inputRef.current?.focus() },
     };
   }
   ```

   Ключове тут те, що ref створює хук, а не викликач. Кожен екземпляр отримує свій, тож два поля на сторінці не можуть перетнутись. Саме цієї властивості глобальний селектор дати не може.

3. Чотири місця виклику втрачають `id` і `htmlFor` та беруть два спреди:

   ```tsx
   const authorsFocus = useAuthorsFieldFocus();
   ...
   <Label {...authorsFocus.labelProps}>{t("fields.author")}</Label>
   <AuthorsField {...authorsFocus.fieldProps} invalid={...} onChange={...} value={...} />
   ```

В `edit-series-dialog.tsx` поле рендериться умовно, бо `hasBooks` ховає його за текстом. Опційний ланцюжок це покриває: клік по підпису, коли поля немає, нічого не робить.

### Обсяг

Шість файлів: `authors-field.tsx` та його stories, `book-form.tsx`, обидва `create-series-dialog.tsx` (у `features/books` і в `features/series`), `edit-series-dialog.tsx`. Поведінка не змінюється ніде, крім того, що клік по підпису починає працювати. Правило «виносити на третьому вжитку» тут спрацьовує: місць виклику чотири.

### Побічно

`id="new-series-authors"` захардкоджений і в `features/books/components/create-series-dialog.tsx`, і в `features/series/components/create-series-dialog.tsx`. Якби cmdk цей `id` не викидав, ми б мали дублікат у DOM. Мертвий проп ховає проблему замість того, щоб дати їй проявитись. Після переходу на ref питання зникає саме собою.

## 2. Кнопка «Скасувати» в діалозі томів обходить підтвердження

**Файл:** `apps/web/src/features/books/components/queue-volume-data-dialog.tsx`

Діалог має guard на незбережені зміни:

```tsx
onOpenChange={(next) => {
  if (next) { onOpenChange(true); return; }
  if (dirty) { setDiscardOpen(true); return; }
  close();
}}
```

Escape, хрестик і клік по підкладці йдуть цим шляхом і питання ставлять. А кнопка «Скасувати» на рядку 486 викликає `onClick={onDone}`, де `onDone` це `close`. `close` скидає `dirty` і закриває діалог напряму, повз guard.

Тобто заповнене губиться без попередження саме тією кнопкою, яку для скасування натискають найчастіше. Підтвердження лишається досяжним тільки через Escape або хрестик, що для користувача виглядає як випадковість, а не як правило.

### Пропозиція

Розділити два наміри, які зараз склеєні в один колбек. `VolumeDataForm` має два різні виходи: успішне збереження (guard не потрібен, дані вже поїхали) і відмова (guard потрібен). Зараз обидва ведуть у `close`.

Замінити один `onDone` на два пропси, `onSaved` і `onCancel`. `onSaved` лишається `close`. `onCancel` веде в ту саму перевірку, що й `onOpenChange`:

```tsx
function requestClose() {
  if (dirty) {
    setDiscardOpen(true);
    return;
  }
  close();
}
```

Тоді всі чотири шляхи виходу поводяться однаково, а `dirty` перестає бути прапорцем, який один із них тихо скидає.

## 3. Не перевірено візуально

Рядок «також відоме як …» у списку підказок видавництва перевірений тільки через дерево доступності та мережевий лог. Скріншотів немає, бо Chrome віддавав нульову ширину вікна весь сеанс перевірки. Верстку цього рядка на вузьких екранах (390px) варто глянути очима, бо назва видавництва може бути довгою і рядок стоїть під основним.

## 4. Дублікат у даних, який чекає рішення

У бібліотеці лежать два видавництва з однаковою назвою, що відрізняються лише регістром:

|                                     | id                                     | книг |
| ----------------------------------- | -------------------------------------- | ---- |
| каталожне `Клуб Сімейного Дозвілля` | `f3201daa-b88f-459f-a9b0-5870b6ceb466` | 23   |
| власне `Клуб сімейного дозвілля`    | `9824d330-1a9b-49aa-8a0a-8a59209c5ea3` | 2    |

Злиття доступне в UI, напрямок заданий жорстко, бо джерелом може бути тільки власне видавництво. Операція незворотна: джерело видаляється назавжди. Жодна з двох книг власного видавництва не прочитана і не в списку бажань, остання додана «Дюна» від 12.08.2026.

Створити таку пару наново вже неможливо, бо `resolveOrCreate` прив'язується до єдиного збігу, віддає 409 на двох і ніколи не створює дубль. Ця пара лишилася з часів до дедуплікації.
