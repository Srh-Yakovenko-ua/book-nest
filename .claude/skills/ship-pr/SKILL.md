# Ship a PR

The path from a finished working tree to a verified dev deploy used to take three separate prompts ("прогони і закоміть", "запуш і відкрий PR", "коли CI позеленіє, змерджи") with the user watching CI in between. This skill runs it as one chain. Each step below is a block under `/unlazy`, and the report at the end is its table.

**Scope comes from the request.** `merge` in the arguments, or a merge word in the user's message ("змерджи", "мердж", "merge"), extends the chain through steps 7 to 9. Without it, stop after step 6 and say the PR is ready to merge. A message that limits the chain ("тільки PR", "не мерджи", "без пушу") wins over this skill.

**Call `gh` by its bare name**, never as a path to `gh.exe`: the hook that asks before a merge matches `gh pr merge` literally. When Git Bash cannot find `gh`, prepend its install directory to `PATH` (on the maintainer's machine the `gh-cli-is-installed-but-off-bash-path` memory has it).

## Steps

1. **Check where you stand.** The branch is a feature branch in a worktree, never `dev`, `prod` or the main checkout. `git rev-parse --abbrev-ref @{u}` must not print `origin/dev`; a worktree branch created from `origin/dev` tracks it, which makes `git status` and `git pull` compare against `dev`, and under `push.default=upstream` a bare push would go to `dev`. Run `git branch --unset-upstream` if it does; `fatal: no upstream configured` is the good case. Then `git status --short` and decide file by file what belongs to the change. Scratch files (audit notes, `*.tmp.ts`, prompt drafts) stay out. Stage by explicit path, never `git add -A` or `git add .`.
2. **Blast radius, when contract-shaped.** A change to `packages/shared`, Prisma, a repository or service signature, a request or response body or `core/**` runs `/blast-radius` first (CLAUDE.md §9).
3. **Review, fix, gates.** Run `/fix-loop` on the diff: it launches the reviewers CLAUDE.md §10 names, fixes confirmed findings through the path owners, and ends with `/check`. When the reviewers confirm nothing, run `/check` (`bash .claude/scripts/gates.sh`) once. Include `security-reviewer` whenever `{ git diff --name-only HEAD; git ls-files --others --exclude-standard; } | sort -u | bash .claude/scripts/security-shaped.sh` prints anything; untracked files count, and the commit hook asks until that review has seen them. A diff only under `docs/` or `.claude/` needs only `code-reviewer`, unless the security list says otherwise. Tests are not run here; CI runs them.
4. **Commit.** Write the message to a file in the scratchpad following `/prose` and commit with `git commit -F <file>`. Conventional subject; no em or en dash (plain hyphens, as in `feat(reading-goals)`, are fine); no assistant name; no `.claude/` path or `CLAUDE.md` filename in the text (say "agent config" or "the hooks"). The pre-commit hook runs lint-staged; a hook failure is fixed, never skipped.
5. **Push and open the PR.** `git push -u origin <branch>`. Pre-push skips typecheck and lint only when `gates.sh` stamped exactly this tree; expect the full run (about 3 minutes) when an untracked file stays in the worktree, a fix landed after the gates, or the branch touches a `package.json`, a `tsconfig`, the eslint config, `turbo.json` or the lockfile. Then `gh pr create --base dev --head <branch> --title "<subject>" --body-file <file>`. The body follows `/prose`: what changed and why, what was verified and how, and a plain list of what was not verified.
6. **Watch CI.** `gh pr checks <number> --watch` in the background; you are notified when it exits. If it exits at once with "no checks reported", GitHub has not registered the run yet: wait until `gh pr checks <number>` lists the jobs, then watch again. Then read the result:
   - **Green**: note `gh pr view <number> --json headRefOid` (the commit CI passed on), then go on, or stop here when merging was not asked for.
   - **Red on a known flake**: rerun once with `gh run rerun <run-id> --failed` and watch again. The run id is the `/actions/runs/<id>/` segment of the failing job's link in `gh pr checks <number>`. Known flakes: the notification bell "fetches each payload once across tab switches" test timing out on its lazy panel, and an API shard whose tests all pass but which fails on an ioredis "Connection is closed" unhandled rejection (memories `notification-bell-lazy-panel-flake` and `api-redis-teardown-flake` hold the history).
   - **Red otherwise**: read `gh run view <run-id> --log-failed`, then run `/diagnose` with the hunter chosen by the failing test's path. Fix, commit, push, watch again. After two red rounds, stop and report with the failing test and the log excerpt.
7. **Merge, only when asked.** Read `gh pr view <number> --json mergeable,mergeStateStatus,headRefOid` and merge only when `mergeable` is `MERGEABLE`, `mergeStateStatus` is `CLEAN` and `headRefOid` is still the commit CI passed on: `gh pr merge <number> --merge --match-head-commit <headRefOid>`. The repository keeps merge commits ("Merge pull request #399 from ..."), so no squash or rebase unless the user asks. The hook asks the user to confirm every merge; that dialog is the user's decision, so never look for a way around it, and never use `--admin`.
8. **Watch the deploy.** A push to `dev` starts the Deploy workflow, which runs CI first and builds only the images whose app changed. Take the merge commit from `gh pr view <number> --json mergeCommit`, then poll `gh run list --workflow deploy.yml --commit <sha> --json databaseId,status,conclusion` until a run appears (it can take a few seconds after the merge), and `gh run watch <id> --exit-status` in the background. Red runs follow the same rules as step 6. A `cancelled` run was superseded by a newer push to `dev` (the workflow cancels in progress); follow the newest Deploy run on `dev`, which contains this commit.
9. **Check the deployed app.** The Deploy run already asserts the health endpoint answers `"status":"ok"`, so that proves nothing new. Check the change itself: for UI, `/shots <feature> --base https://dev.book-nest.net` when the feature has a screen list, otherwise one Chrome MCP pass on the changed page; for an endpoint, a read-only curl or the page that calls it. When the run's "Build API image" job ran, also confirm the new API container answers: `curl -s https://dev.book-nest.net/api/health` gives `timestamp` and `uptimeSeconds`, and `timestamp - uptimeSeconds` (when the process started) must be later than the `startedAt` of the "Deploy over SSH" job in `gh run view <id> --json jobs`. A change with nothing to look at (agent config, docs) ends at the green Deploy run; say so. Never change data to prove a deploy.

## Report

Close with the `/unlazy` table: one row each for review and gates, commit (short SHA), PR (link), CI (result per run, reruns named), and when merging was asked, merge (merge commit), deploy (run result) and the post-deploy check (what was observed). **Missing** lists every step not run and every NOT_VERIFIED an agent returned.

## Traps

- **A green PR is not a green deploy.** The PR runs the tests affected since its base; the push to `dev` runs the tests affected since the last successful deploy, which also covers anything else merged since then, and both switch to the full suite on shared, Prisma or lockfile changes. That is why the deploy watch is part of the chain.
- **The gates need the user's words.** The hook lets `gates.sh` run only when the user's last message holds a slash command or a word such as commit, push, коміт, пуш, прогони, PR, merge, мердж, мерж, ship, доведи, check or CI. A request phrased without any of them gets the gates denied; then ask the user to type `/ship-pr` or "прогони", and do not run the checks another way. Local test runs stay denied and are not needed: CI is the test run.
- **Merging is the user's call even inside this skill.** A request that only says "відкрий PR" does not authorise a merge, and a merge approved for one PR does not carry over to the next.
- **Release work is elsewhere.** Promoting `dev` to `prod` goes through `release-manager`, never through this chain.
